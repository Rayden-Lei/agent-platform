# 智枢·智能体平台 开发规范（通用）

版本 V2.3 · 2026-09-06

> 本文档与 `06-后端规范.md`、`07-前端规范.md` 共同构成项目规范。
> 项目规范优先于个人或全局规范；**项目的存量代码现状不构成规定**，满仓库都这么写不等于这么写是对的。
> 条款分级：未标注的一律**必须**（违反 = 返工）；标【建议】的可按场景权衡。

## 1. 铁律

违反任一条都是事故，不是风格问题。每条后面括号里是它的来历。

1. **改前读完整文件，用精确替换编辑**。禁止只读前 N 行再整体写回（曾截掉 `runs.py` 的 get 接口导致 404）。
2. **改完必验，验证通过才算完成**。后端：`from app.main import app` 能导入 + `pytest` 通过 + 接口改动用脚本或 curl 真实调一次；前端：`npx tsc --noEmit` + `npm run build` 通过；界面改动由使用者决定谁来做人眼验证，不自作主张。
3. **错误不吞**。禁止 `except Exception: pass`、禁止捕获后只 `rollback` 不记录。要么处理，要么带上下文重抛，要么 `logger.exception` 后注释为什么可以忽略（调度器吞异常，静默产生 1800 多条永久 running 的记录）。
4. **运行记录只能通过 `run_service.create_run / finalize_run` 创建与收尾**。任何新的执行入口都不许自己 `Run(...)`（三处各写一份收尾逻辑，没有一处写 finished_at）。
5. **循环内不发 IO**。查库、调接口、读文件一律批量取回后内存装配。
6. **密钥不进仓库，不进日志**。`.env` 已忽略；`.env.example` 必须能直接 `cp` 后启动（曾有两个键粘在一行导致启动即报错）；日志、异常信息、接口响应里不出现密码、token、API 密钥。
7. **共享环境的破坏性操作先确认**。删数据、`DROP`、无条件 `UPDATE / DELETE`、改线上配置、重启服务进程，先说明影响面再等确认。开发库可能就是服务器在用的库。
8. **契约一次切换到底**。改字段名、接口路径、枚举值时同批改完路由、服务、前端 api 层、页面、`04-接口设计.md`；不留 `新字段 || 旧字段` 兜底。
9. **表结构变更必落幂等迁移脚本**并更新 `03-数据库设计.md`。`create_all` 只建新表，不改列。
10. **不重复造轮子**。技术栈固定：FastAPI、SQLAlchemy 2.0、pydantic-settings、LangChain / LangGraph、pgvector、APScheduler、React 18、Ant Design 5、React Flow、zustand、axios。引入新依赖先说明标准库或现有依赖为什么做不到。
11. **测试脚本落成 `.py` 文件再运行**，不用 shell 内联复杂 JSON（引号转义反复出错）。
12. **需求有两种差异很大的合理解读时先问**，只问真正卡住的那一点，其余照常推进。

## 2. 工作流程

### 2.1 从需求到交付

1. 对照 `01-需求说明.md`：需求不在里面先补文档，再动代码。
2. 动手前看 2–3 个同类既有实现确定口径：路由看 `api/v1/agents.py`，服务看 `services/agent_service.py`，页面看 `pages/Agents.tsx`，测试看 `tests/test_runs.py`。
3. 改动超过约 10 个文件或跨越多个模块，先给拆分方案：分几步、每步改什么、每步怎么验证；每步都能独立编译运行。
4. 每完成一个功能点立即验证，不攒到最后。
5. 交付说明四要素：改了什么（文件与要点）、为什么、验证了什么 / 没验证什么、需要对方决定的点。未完成、已知风险、临时绕过的地方单独列出。

### 2.2 找参照，不凭猜

"与项目统一"的唯一可靠来源是既有代码。命名风格、错误抛法、目录位置、注释语言都照着写。不确定某个 API、方法、配置项是否存在，去读源码或文档确认，不凭印象写。

## 3. 命名

| 领域 | 规则 | 例 |
|---|---|---|
| Python 模块、函数、变量 | snake_case | `run_service.py`、`finalize_run` |
| Python 类 | PascalCase | `KnowledgeBase`、`BizError` |
| Python 常量 | UPPER_SNAKE | `FINAL_STATUSES`、`RRF_K` |
| 服务函数 | 动词前缀：`list_ / create_ / get_ / update_ / delete_ / <动作>_` | `publish_agent`、`execute_workflow` |
| 私有函数 | 下划线前缀 | `_calc_cost` |
| TypeScript 变量、函数 | camelCase | `loadConversations` |
| React 组件、类型 | PascalCase | `AssistantMessage`、`ToolStep` |
| 前端 api 函数 | `listXxx / createXxx / updateXxx / deleteXxx / <动作>Xxx` | `publishAgent`、`chatAgentStream` |
| 文件名 | 页面与组件 `PascalCase.tsx`；其余 `camelCase.ts` / `snake_case.py` | |
| 数据库 | snake_case；布尔 `is_ / has_`；时间 `_at`；外键 `<单数>_id` | `is_enabled`、`finished_at`、`kb_id` |
| URL | 小写复数名词，连字符 | `/knowledge-bases/{id}/documents` |

同一概念全项目一个词：知识库在 URL 里叫 `knowledge-bases`、代码里缩写 `kb`；运行记录 `run`；会话 `conversation`；消息 `message`；工具 `tool`。不要再造 `client / customer`、`job / task` 这类同义词。

布尔量用肯定语义（`is_enabled` 而非 `disabled`）。禁止数字尾缀（`data1`）和无意义缩写（`usr`、`mgr`）。

## 4. 注释与文档

- 代码注释、提交信息、文档一律中文；技术术语保留英文。
- 注释写 **why**：为什么这么做、为什么不用更直观的写法、魔法值从哪来、已知的坑。代码本身已经说明 what。
- 公共函数写 docstring：用途、参数约束、返回值、异常、副作用。
- 注释与代码同批更新，过期注释比没有更有害。
- 文档维护矩阵：

| 改了什么 | 必须同批更新 |
|---|---|
| 功能范围、角色权限 | `01-需求说明.md` |
| 分层、核心链路、设计决策 | `02-架构设计.md` |
| 表、列、索引、JSON 字段结构 | `03-数据库设计.md` + 迁移脚本 |
| 路由、请求响应字段、SSE 事件 | `04-接口设计.md` + `frontend/src/api/<域>.ts` |
| 页面骨架、列表 / 详情 / 统计的写法、页面改造批次 | `07-前端规范.md` + `14-页面深度优化方案.md` |
| 环境变量、启动方式、部署步骤 | `08-运行与部署.md` + 两份 `.env.example` + `docker-compose.yml` |
| 规范本身 | 本文档或 06 / 07，并在"已犯过的错"追加来历 |
| 已知问题、改进项 | `09-演进路线.md` |

## 5. 错误处理与日志

- 服务层抛 `BizError(status_code, detail)`，detail 是可直接展示给用户的中文；全局处理器转成 `{"detail": ...}`。服务层不抛 `HTTPException`，不依赖 HTTP 上下文。
- 区分**预期内的业务失败**（不存在、无权、被引用、未发布）与**意外故障**（连接断、空指针）：前者 BizError，后者记录完整堆栈后走 500 或落到运行记录的 error。
- 抛出时带足上下文：哪个操作、哪个 ID、什么条件不满足。"参数错误"是无效信息。
- 外部调用（模型、HTTP 工具、MinIO、Redis）必须有超时；重试要有上限，只重试幂等操作。
- **超时要真的能中断等待**：`Future.result(timeout=...)` 只让调用方不再等，线程仍在跑。
  用 `with ThreadPoolExecutor(...)` 包住它等于白设超时 —— 退出时的 `shutdown(wait=True)` 会一直等到慢调用返回。
  需要超时保护时显式 `finally: executor.shutdown(wait=False)`。
- 捕获异常优先写具体类型；预期内的降级打 `warning` 并写清降到了什么，意外故障 `logger.exception` 留堆栈。详见 `06-后端规范.md` 第 13 节。
- 日志：每个模块 `logger = logging.getLogger(__name__)`；`ERROR` 需要人介入、`WARN` 异常但已自愈、`INFO` 关键业务节点、`DEBUG` 排查细节。带上业务主键（run_id、agent_id、job_id）。批量操作打汇总不逐条。日志本身不能抛异常、不能改变程序行为。

## 6. 测试

- 修缺陷先写一个能复现的用例（此时应失败），再改代码让它通过。
- 新增业务规则至少一条用例；**负向用例比正向重要**：非法迁移、无权、重复提交、空集合、超界。
- 断言到具体值或错误信息片段，不只断言"没抛异常"。
- 用例名写业务意图：`test_scheduled_job_disabled_is_skipped`，不写 `test1`。
- 数据自己造、自己清：名称带 `pytest-` 前缀，`try / finally` 清理，删父记录靠外键级联。用例之间不共享可变状态、不依赖顺序。
- 测试连接 `.env` 指向的真实数据库，且会启动调度器；如果那是共享库，不要在里面创建启用状态的定时任务。
- CI 门禁：新增失败零容忍；依赖外部模型可用性的用例不进门禁。

## 7. 版本控制

- 提交信息 `type: 中文摘要`，type 取 `feat / fix / refactor / improve / perf / docs / test / chore / build`；scope 可省（沿用历史）。正文写问题、改动、验证，需要时写影响面。
- 一个提交做一件事，能独立回滚；格式调整与功能改动分开；生成产物（`docs/*.docx`）随源文档改动一起提交，不手改。
- 提交前：当场跑验证不引用旧结果；自查 diff 无调试代码、无注释掉的旧代码、无无关格式改动、无密钥与本地配置。
- 推送前 `git pull --rebase`；`main` 不强推。
- 当前单人开发直接在 `main` 提交；多人协作后改为 `feat/ / fix/` 分支加 PR，CI 通过后合并。

## 8. 安全底线

- 服务端是校验的唯一权威，前端校验只是体验。
- 一切外部输入不可信：长度、类型、枚举取值都要校验；文件上传按扩展名分发解析，不信任 content-type。
- SQL 一律 SQLAlchemy 表达式；迁移脚本里的 f-string 只能拼常量，条件值走参数绑定。
- 行级越权：会话按 `user_id` 校验；知识库按角色过滤；新增"某个用户的资源"类接口必须做同样的判断。
- 模型密钥 AES 加密入库，接口不回传；API Key 只存哈希。
- 代码执行节点是无沙箱的 `exec`，HTTP 节点与工具可访问任意地址：工作流编辑权限只给可信内部用户，对外开放前必须先收口（见演进路线）。
