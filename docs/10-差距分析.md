# 智枢·智能体平台 差距分析：面向企业级 AI 能力中台

版本 V0.1 · 2026-09-04 · 本文档为一次性的现状盘点，不作为与代码持续同步的"活文档"

> 本文档回答一个问题：**当前平台离"企业级统一 AI 能力中台"还有多远**。
> 它基于一份企业级中台的 6 层标准架构目标（业务应用层 → AI 应用编排层 → 核心服务层 → 模型引擎层 → 数据底座层 → 算力基础设施层，外加多租户权限、可观测运维、安全合规三大贯穿体系），逐层对照当前代码与实际能力。
> 所有"已具备 / 部分 / 缺失"的判断以 `01-需求说明.md`、`02-架构设计.md`、`09-演进路线.md` 与后端代码为准，不是以计划为准。

## 0. 总体结论（先读这段）

**当前平台是一套工程规范良好、功能扎实的"私有化 MVP 一期底座"，不是企业级 6 层中台。**

- 对照**企业级完整 6 层蓝图**，真实完成度约 **30%**。缺的不是工程质量，而是三大类结构性能力：**多租户、规模化治理（统一网关 / 微调 / 资产市场）、算力与基础设施形态（K8s / GPU）**。
- 对照目标文档自带的 **MVP 一期精简架构**，完成度约 **70～80%**——基础编排、统一接入、RAG、基础存储、基础安全监控这几条线已经走通且做了工程加固（请求追踪、幂等收尾、降级可见、统一分页）。
- **多租户是离目标最远、也最决定性的缺口**：18 张业务表无任何 `tenant / org / project` 字段，无租户隔离、无项目空间、无企业 SSO。由于租户维度在建表时就该定，等真实多业务线出现后再回填成本极高，属"该提前布局但别空转"的一类。

> 写文档的立场与 `09-演进路线.md` 一致：在出现真实调用方与真实多业务线之前，不应为完整 6 层投入（不拆微服务、不上 K8s、不接 MCP）。差距分析的价值是"知到差距、定好优先级"，不是"马上把 6 层全做出来"。

## 1. 评估方法

- **对照基准**：企业级 6 层标准架构 + 三大贯穿体系（见文末附录 A 摘录）。
- **证据来源**：当前后端 `app/` 代码、`app/db/models.py` 全部 18 张表、`docker-compose.yml`、以及 `docs/01 / 02 / 09`。
- **判定口径**：✅ 已具备（代码已有且可用）；🟡 部分（有基础，缺目标要求的某项或未闭环）；❌ 缺失（无实现或有代码但链路未闭合）。
- **局限**：本分析是能力清单盘点，不代表真实运行性能/nuance 质量——那些需要实际环境验证。

## 2. 逐层对照

### 2.1 第一层：业务应用层（中台输出端）

| 目标组件 | 现状 | 判定 |
|---|---|---|
| 智能对话应用 | 智能体对话 + SSE 流式 + 多轮记忆 + 工具 + RAG 引用来源，完整可用 | ✅ |
| 智能文档应用 | RAG 已能基于文档问答；摘要/翻译/比对/合同审核**无** | 🟡 |
| Agent 业务应用（办公/巡检/数据查询） | 有 Agent 配置与运行骨架；**无现成业务 Agent 模板**，需业务方编排自建 | 🟡 |
| 第三方业务系统对接 | 有通用 HTTP 工具可对接任意接口；**无 OAuth 凭证托管、无连接器、无账密管理**，每次对接手工配 headers | 🟡 |

> 这一层本质是"中台能力的使用方"。平台定位正确（不直接做业务应用，而是提供能力给上层），**本层不算硬缺口，缺口在下层能力是否足够**。

### 2.2 第二层：AI 应用编排层（中台生产力层）

| 目标组件 | 现状 | 判定 |
|---|---|---|
| Prompt 工程中心 | **无**：无 Prompt 模板管理、无版本管控、无变量配置中心、无在线调试。Prompt 只散落在智能体 `system_prompt` 或节点配置里，无版本 | ❌ |
| 可视化工作流编排 | 10 类节点（agent/tool/条件/kb/code/http/loop/human_review/start/end），拖拽 + 编辑内测试运行；**缺并行(parallel)分支**，当前只有 true/false 条件边与 loop 回环 | 🟡 |
| Agent 智能体编排 | 角色设定 ✅、工具挂载 ✅、RAG 装配 ✅、版本发布与回滚 ✅；**长期记忆、任务规划、多 Agent 协同无** | 🟡 |
| 应用快速发布 | 有智能体"发布"（版本快照）；**无一键发布成 API / 嵌入式组件 / 演示页**；对外依赖 API Key + 接口 | 🟡 |

**本层重点缺口**：① Prompt 工程中心完全缺失（最明显空位，直接关系中台"低代码生产力"定位）；② 工作流缺并行 fan-out 节点。

### 2.3 第三层：AI 中台核心服务层（能力中枢，重点层）

| 目标组件 | 现状 | 判定 |
|---|---|---|
| 统一 API 网关 | 无独立网关。FastAPI 路由即入口：鉴权 ✅、API Key 按次扣配额 ✅；**无限流（仅登录限流）、无熔断、无黑白名单、无流量管控** | 🟡 |
| 模型管理服务 | 多模型接入 ✅（OpenAI 兼容）、增删改查 ✅、连通测试 ✅；**无上下线(仅 is_enabled)、无模型评测、无模型选型、无版本管理实体** | 🟡 |
| RAG 知识库服务 | 文档接入 ✅、解析(8 格式含 OCR) ✅、切片 ✅、向量化 ✅、向量+关键词双路召回 ✅、RRF 融合 ✅、检索再鉴权 ✅；**唯独重排序是词法重排而非 Rerank 模型** | 🟡 |
| 模型微调服务 | **无**：无数据集管理、无 LoRA/SFT、无训练调度、无导出 | ❌ |
| 资产市场服务 | **无**：无能力上架/订阅/调用计量/复用 | ❌ |
| 会话&日志服务 | 会话上下文 ✅、运行记录 ✅、Token 用量统计 ✅、审计 ✅；**数据溯源 ❌**、全链路日志是应用日志带 request_id（够用但非独立"服务"） | 🟡 |

> **本层是当前与"企业级中台"差距最大的一层**：现在的能力是"自用型单体内部模块"，目标的第三层是"对外输出的能力中枢 + 资产化 + 治理"。

### 2.4 第四层：模型引擎层（推理/训练算力）

| 目标组件 | 现状 | 判定 |
|---|---|---|
| 公有大模型引擎 | chat 统一走 ChatOpenAI 兼容协议，天然可对接通义/DeepSeek/GPT 等；embedding 同类 | ✅ |
| 私有化模型引擎 | LangChain + OpenAI 兼容协议，本地 vLLM 等自带的 OpenAI 服务也能接入；**但平台不管理模型部署/生命周期** | 🟡 |
| 推理引擎 | 流式 ✅；**批量 ❌、动态扩缩 ❌、并发调度无（单进程）** | 🟡 |
| 训练引擎 | 同微调服务，完全缺失 | ❌ |

### 2.5 第五层：数据底座层

| 目标组件 | 现状 | 判定 |
|---|---|---|
| 向量数据库 | pgvector + 切片（`document_chunks`） | ✅ |
| 业务结构化数据库 | PostgreSQL，18 张表（用户/模型/智能体/工作流/运行/会话/审计等） | ✅ |
| 对象存储 | MinIO | ✅ |
| 数据集仓库 | **无**训练/评测数据集存储治理 | ❌ |
| 日志时序存储 | 应用日志 + `audit_logs` 表；**无独立时序库/指标采集/监控大盘** | 🟡 |

> 数据底座已经搭对方向（Postgres + pgvector + Redis + MinIO 五服务），缺的是为微调服务的"数据集仓库"和独立时序存储。

### 2.6 第六层：算力基础设施层

| 目标组件 | 现状 | 判定 |
|---|---|---|
| GPU 算力集群 | **无**，当前是通用 CPU 容器 | ❌ |
| 容器调度平台（K8s） | **Docker Compose 5 容器，无 K8s、无服务编排、无弹性扩缩** | ❌ |
| 服务器&网络 | 私有化部署 ✅（Compose 或裸机）；**无多节点、内网安全网络由外部环境决定** | 🟡 |

> 本层缺口最大但最特殊——它是"部署形态"而非"功能"。当前**单体 + Compose** 是 `09-演进路线.md` 明确的有意决策（真实调用方出现前不拆微服务）。是否上 K8s/GPU，应取决于真实多业务线负载，而非现在空转。

### 2.7 三大贯穿支撑体系（企业级硬门槛）

| 体系 | 现状 | 判定 |
|---|---|---|
| **多租户&权限** | **多租户 ❌**：18 表无 tenant/org 字段，无租户隔离、无项目空间、无企业 SSO。RBAC 仅三级角色（admin/developer/caller）+ 路由级鉴权 + 极少数行级（会话本人、知识库可见角色）。目标要求的"模型/知识库/工作流/API 细粒度资源隔离"**未实现** | ❌ |
| **运维监控&计量** | 中间件(X-Request-Id/访问日志) ✅、运行记录 ✅、降级状态 ✅、API Key 配额 ✅、审计 ✅；**无监控大盘、无 QPS/耗时/错误率图表、无 GPU/CPU 指标、无租户配额、无告警** | 🟡 |
| **安全&合规** | 基础 ✅：JWT/RBAC/模型密钥 AES/登录限流/审计/API Key；**无输入输出内容审核、无敏感信息脱敏、无合规级输出溯源、无合规留痕体系** | 🟡 |

> **多租户是与目标距离最远、也最决定性的缺口**——目标明确要求"多业务线复用"，没有租户隔离就无法真正做到多业务线独立隔离与按租户配额计量。

## 4. 建议路径（按价值/成本排序）

与 `09-演进路线.md` 的精神一致：在出现真实调用方与真实多业务线之前，不应为完整 6 层投入。以下分三档。

### 4.1 短期（接住真实调用方，成本低、直接提升可用性/中台定位）

- **入站网关治理最小项**：给现有接口入口补**限流 / 熔断 / 黑白名单**（外部系统走 API Key 调用时尤其需要）。
- **Prompt 模板管理**：最小可用版（模板 + 变量 + 版本），成本低、直接补上编排层最大空位。
- **对话摘要持久化、工作流并行节点、工具参数 JSON schema**：三项均已在 `09-演进路线.md` 第二梯队列出，做掉即补齐编排层硬伤。

### 4.2 中期（出现真实多业务线前布局）

- **多租户**：这是唯一"建表时就要定、事后回填成本极高"的缺口，建议先做**轻量租户 + 行级资源隔离**骨架（`tenant_id` 外键 + 资源归属 + 可见性过滤），而非空转迟迟不动。其余细粒度资源权限、企业 SSO 可视业务需要跟进。
- **Rerank 模型接入**：现有词法重排可视为降级，Rerank 模型接入后检索质量上一个台阶。

### 4.3 明确不做（确认真实负载前不投入）

- **GPU / K8s**、**微调训练引擎**、**资产市场**、**企业 SSO**：在没有真实调用方、真实多业务线负载之前，属"给 demo 加 demo"，不做。

## 5. 附注：判断依据的有限性

- 本分析是**能力清单盘点**，不代表真实运行性能、高并发表现或检索质量——这些需要实测。
- 文档 `03-数据库设计.md` 所述表数量与当前 `db/models.py` 实际表数量存在出入（README 引用时称 17 张，代码为 18 张），属存量文档与代码漂移，不在本次评估范围内（后续可在维护文档时顺手校正）。

## 附录 A：企业级 AI 能力中台 6 层目标（评估基准摘录）

- 第一层 业务应用层：智能对话 / 智能文档 / Agent 业务应用 / 第三方业务系统对接。

- 第四层 模型引擎层：公有+私有模型引擎 / 推理引擎(流式·批量·扩缩·调度) / 训练引擎。
- 第五层 数据底座层：向量库 / 业务库 / 对象存储 / 数据集仓库 / 日志时序存储。
- 第六层 算力基础设施层：GPU 集群 / K8s / 服务器与网络。
- 贯穿体系：多租户权限 / 可观测运维计量 / 安全合规。
