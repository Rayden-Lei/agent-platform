# 16 · 运行时借鉴设计：AgentScope 2.0 对照与改造方案

> 状态：方案稿（2026-10-26），未开工。结论先写在第 0 节，实施拆分在第 4 节。
> 对照基准：AgentScope 2.0 文档（2.0.11dev）、AgentScope 1.0 论文（arXiv 2508.16279）。
> 本文只讨论**对话运行时**（`chat_runner` + `chat_service` + `tools`），工作流引擎不在范围内。

---

## 0. 结论

1. **不换框架。** 现有 LangGraph `create_react_agent` + 自建执行器的组合，在工作流确定性编排上比 AgentScope 更贴合本项目；要补的是运行时的**契约层**与**闸门层**，不是引擎。
2. **值得学的四件事，按性价比排序**：
   - **P0 事件契约**（事件带 `seq` / `reply_id` / 状态字段，且"事件流可重建消息"）—— 1.5 人天，纯增量，是后续三项的地基。
   - **P3a 工具执行闸门**（执行前 deny + 审计，不做 HITL）—— 1 人天，补真实安全缺口（HTTP 工具可访问任意地址）。
   - **P1 中间件收口**（3 个钩子，不做 6 个）—— 2 人天，把轮数守卫、trace、预算、闸门收进一层。
   - **P2 上下文 offload**（工具结果全文可回读）—— 1 人天，解决"截断 200 字后模型只能重调"。
3. **明确不学**：Agent Team / A2A、SSE 断点续传、5 档权限模式矩阵、工具组运行时动态启停。
   理由逐条写在 §6，避免以后被"别人有我们也要有"重新拉回来。
4. **与现有路线图合并**：P0 是 `15` 号文档 OP-08（调用链持久化）的前置，P1 与 OP-08、AG-09 合并做，不另开批次。

- 工具结果落库的是截断后的文本，重建出的消息 ≠ 真实执行结果。

## 2. AgentScope 2.0 的五个模型（只摘与本案相关的）

### 2.1 Msg / Event 双抽象

- `Msg` 是落库与通信单位，含 `finished_reason`（completed / interrupted / exceed_max_iters / error）与 `usage`。
- `Event` 是流式单位，`start → delta → end`，用 `reply_id` / `block_id` / `tool_call_id` 三级关联。
- 关键契约：**一次 reply 的全部事件，按序 `append_event` 到一条 Msg，结果与最终落库一致**。官方给了 `append_event` 的逐事件映射表。
- `ToolCallBlock.state`：pending / asking / allowed / submitted / finished；`ToolResultBlock.state`：running / success / error / interrupted / denied。

### 2.2 中间件

6 个洋葱钩子（`on_reply / on_reasoning / on_acting / on_model_call / on_compress_context`）+ 1 个 transformer（`on_system_prompt`）+ `list_tools`。
最有价值的能力不是"能观察"，而是**能改控制流**：`on_reply` 里吞掉 `ReplyEndEvent` 不往下传，agent 就会再跑一轮。

### 2.3 工具组

`Tool / Toolkit / ToolGroup` 三层，`basic` 组常开，`ResetTools` 元工具让模型运行时切换。治"工具过多导致选不准"。

### 2.4 权限

三段式：规则（deny → ask → allow 的优先级链）× 模式（DEFAULT / ACCEPT_EDITS / EXPLORE / BYPASS / DONT_ASK）× 工具级检查（`check_read_only` 快路径、危险路径、`bypass_immune` 安全 ASK）。
还有一个细节值得抄：**只读判定按"这次调用"而不是"这个工具"**（`git status` 只读，写文件的 bash 不是）。

### 2.5 上下文

三层装配：`system_prompt`（base + skill + 中间件变换）→ 压缩摘要 → 近期原文。
三个机制：注入（运行时提示）、压缩（摘要 + 工具结果截断）、offload（丢掉的全文落外部存储，可回读）。

## 3. 差距矩阵

## 4. 改造方案

> 小节顺序就是建议实施顺序：P3a 提前到 P1 之前，是因为它独立、改动面小、收益最直接；代号保留原设计里的 P 编号，不重排以免与 §5 的路线图对不上。

### 4.1 P0 事件契约（1.5 人天）

**状态**：已完成（2026-10-26，提交见本节末尾「实现记录」）。

**目标**：事件成为可校验、可重建、有终态的一等对象，同时**不破坏现有前端**（只加字段，不改类型）。

**改动点**

1. 新增 `backend/app/services/chat_events.py`：
   ```python
   FINISHED_REASONS = ("completed", "interrupted", "exceed_max_iters", "error")

   class EventStream:
       """一轮对话的事件产出口：单调 seq + reply_id，最终可重建消息。"""
       def emit(self, type_: str, **payload) -> dict      # 自动补 seq / reply_id
       def rebuild(self) -> dict                          # 事件流 → 消息字段
   ```
   `rebuild()` 的映射（与 AgentScope `append_event` 同构，但字段按本项目现状）：

   | 事件 | 重建结果 |
   |---|---|
   | `delta` | `content += evt.content` |
   | `tool_call` | 追加 `{id, name, args, status: "running"}` |
   | `tool_result` | 按 `tool_call_id` 回填 `status`（done/error/denied）与 `result` |
   | `citations` | `citations = evt.citations` |
   | `done` / `error` | `finished_reason`、`usage` |

2. `_agent_events`（`chat_runner.py:152`）改为经 `EventStream.emit` 产出：
   - 所有事件带 `reply_id = f"run-{run_id}"`、`seq` 从 0 递增；
   - `tool_call` 增加 `state: "running"`；`tool_result` 增加 `state: "done" | "error"` 与 `truncated: bool`、`chars: int`；
   - `done` 增加 `finished_reason: "completed"`；`error` 增加 `finished_reason: "error" | "exceed_max_iters"`；
   - `interrupted` 由**前端**在用户点停止时本地收尾（`useChatStream.stop()` 已经知道是主动中断），服务端不补发事件——客户端已断连，补发也送不到；服务端 `finally` 的落库与 `run.status=cancelled` 保持不变。

3. 落库走同一份重建结果：`stream_chat` 收尾时用 `state.rebuild()` 写 `messages`，保证"事件流 == 落库"由同一函数产生，不靠两处各自拼。

4. 工具结果**落库不截断**：下发仍 `TOOL_RESULT_PREVIEW_CHARS=200`，落库用 `TOOL_RESULT_STORE_CHARS=8000`。现状两者共用同一份截断，是"可重建"契约的直接漏洞（`chat_runner.py:216-218`）。
   **2026-10-26 已做**（只拆数值，`truncated` 标记未加：`tool_calls` 结构不变，落库超过 8000 字时静默截断）。

5. ~~SSE 加事件 id~~ **实现时取消**：`seq` / `reply_id` 放在事件体内，帧格式不变。原方案假设"前端只解析 data 行"是错的——前端用 fetch 手工解析，按整块 `part.startsWith("data: ")` 判断事件，多一行 `id:` 会让整块被丢掉；而且不是 `EventSource`，浏览器不会拿 id 做 Last-Event-ID 重连。将来做续传按事件体内的 `seq` 重放。

**实现记录（2026-10-26，与方案的出入）**

1. `chat_events.py` 提供 `StreamState`（从 `chat_runner` 移过来，加了 `citations` / `finished_reason` / `final_usage`）、`EventStream`（只补 `seq` / `reply_id`）、`apply_event`（实时累积与重放共用）、`reduce_events`（纯重放）。没有单独的 `rebuild()` 方法：落库真相是 `StreamState`，重建能力由 `reduce_events` 承担，单测对比两条路径。
2. 工具事件加了 `state`（`running` / `done` / `error`），落库的 `messages.tool_calls` 也随之多一个 `status` 字段（前端历史映射忽略它，按 `done` 渲染）；`truncated` / `chars` 没加，留给后续按需。
3. 同一工具调用的 `tool_call` 事件做了去重：完整 chunk 与 `ToolMessage` 可能各报一次，事件流里只允许一条，否则重放会多出一个工具卡片。
4. 落库仍走 `StreamState`（`apply_event` 累积），没有另写一份"重建后落库"，等价性由 `reduce_events` 的单测保证。

**验收**

- 单测：对一段固定事件序列调用 `rebuild()`，结果与 `messages` 表落库行逐字段相等（含 `tool_calls` 的 `state`、`usage`、`finished_reason`）。
- 单测：`seq` 连续无重复；`reply_id` 全流一致。
- 回归：`tests/test_chat_runner.py` 现有 9 例全绿；`test_agent_debug.py`、`test_shares.py` 全绿。
- 手验：前端对话、调试、分享三处行为不变（新增字段被忽略）。

**风险**：低。行为变化只有两处：`tool_calls` 落库从 200 字变成最多 8KB（`messages` 行会变大，`GET /conversations/{id}/messages` 的响应随之变大，需确认前端消息列表不做整表渲染）；前端停止时补 `finished_reason` 的本地收尾要确认不影响"重新生成"（`useChatStream` 的 `regenerate` 只依赖消息列表，不读该字段）。

### 4.2 P3a 工具执行闸门（1 人天）

**状态**：已完成（2026-10-26）。实现记录见本节末尾。

**目标**：在**执行前**拦一道，补上"工具进了 tool_ids 就能调任意地址"的缺口。不做 HITL。

**改动点**

1. 新增 `backend/app/tools/permission.py`：
   ```python
   @dataclass(frozen=True)
   class ToolCallContext:
       tool: Tool
       agent_id: int
       run_id: int
       source: str          # chat / debug / share / api_key / schedule
       args: dict

   def check(ctx: ToolCallContext) -> tuple[str, str | None]:
       """返回 ("allow" | "deny", 原因)。deny 的原因会作为工具结果回给模型。"""
   ```
   首版规则（硬编码，不进库，避免过度设计）：
   - `tool.is_enabled == False` → deny（对话装配层已过滤、工作流引擎在 `engine.py:252` 也查，这里只是把同一判断收进一个入口）；
   - `source == "share"` 且 `tool.type == "http"` → deny（分享访客的闸门目前只在装配层 `chat_service.py:347`，执行层再兜一层）；
   - HTTP 工具的目标 URL **必须命中 `tool.config.allowed_hosts`**（新增字段，空 = 不限制但打 WARN 并写审计）——这是本次最实的收益，直接堵住 SSRF 与"改配置指向任意内网服务"；
   - `calculator` / `current_time` → 恒 allow（只读、无副作用）。

2. `Tool.config` 增加 `allowed_hosts: list[str]`（主机名后缀匹配，如 `["api.internal.example.com"]`），工具页表单加一项，`PUT /tools/{id}` 校验格式。

3. 闸门挂在 `_execute_http` 入口（`executor.py:120`）**之前**，由 P1 的 `on_acting` 中间件调用；P0 阶段可先直接调 `check()`，P1 再挪进中间件，避免两次改调用点。

4. deny 的留痕：`tool_calls` 里记 `status: "denied"` + 原因；写审计 `tool_denied`（resource=tool，detail 带 agent_id / run_id / 目标 host / 来源）。**不记 args 全文**，只记键名，避免把业务参数写进审计。

**实现记录（2026-10-26，与方案的出入）**

1. 新增 `app/tools/permission.py`：`ToolCallContext`（tool + source + agent_id + run_id）、`check()`、`log_decision()`。闸门挂在 `_execute_http` 开头，对话、工作流、工具页测试三条路径都被覆盖；`execute_tool` 的 `ctx` 默认 `None`（按未知来源处理，HTTP 工具照样走白名单判定）。
2. 来源：`ChatTurn.source`（chat / api_key / share，路由按会话通道填）、`build_debug_context` 传 debug、工作流节点传 workflow、工具页测试传 admin_test（跳过白名单，否则新工具配不了）。
3. `allowed_hosts` 只对 HTTP 工具生效，保存时校验（400）：数组、最多 20 项、只写主机名。**当天收口**：空名单从"放行 + WARN"改成拒绝（对话 / API Key / 工作流），只有 `admin_test` 例外；前端表单把 HTTP 工具的白名单设为必填，后端保存仍不拦（存量工具要先补配置）。收口后这道闸门才真正成立——放行等于没有。
4. deny 返回 `{"error": ..., "denied": True}` 且不发请求：`_agent_events` 据此把 `tool_result.state` 与落库的 `tool_calls.status` 标成 `denied`（与执行失败区分），工作流节点直接 failed。
5. **没做审计**：原方案要写 `tool_denied` 审计，但工具执行层没有 db session，异步路径里同步写库还会阻塞事件循环。deny 目前进日志（含 tool / source / agent / run）+ `tool_calls.status`，审计留到 P1 中间件里统一做。
6. 前端工具表单加了「目标地址白名单」多行输入（每行一个主机名，也接受逗号），HTTP 工具必填；清空即删除该键，执行时按"未配置"拒绝。

**验收**

- 单测：停用工具在对话、调试、工作流三条路径都被 deny；
- 单测：`allowed_hosts` 为空时 deny（**审计未做**，见实现记录第 5 条）；不在白名单时 deny 且模型收到"该工具在当前环境不可用"；`admin_test` 在空名单下仍放行；
- 单测：分享访客即使误配了 HTTP 工具也调不出去；
- 手验：现有 HTTP 工具（配了 `allowed_hosts`）正常调用。

**风险**：中。收口后，**未补白名单的存量 HTTP 工具在对话与工作流里会立刻全部失败**（错误文案是"工具 X 未配置 allowed_hosts，无法判断目标地址是否可信"）。这是有意为之：请先在工具页逐个补齐并测试，再上线；上线顺序建议"先补配置、后发后端"，否则先发后端会让存量工具直接不可用。

### 4.3 P1 中间件收口（2 → 3 人天）

**状态**：落点已复核（2026-10-26），未开工。

**目标**：把 `chat_runner` 里的轮数守卫、闸门、trace，以及 gateway 的熔断，收进一层协议；以后加能力只写一个类，不改主流程。

**可用的落点（2026-10-26 实测 `langgraph==1.2.11`）**

`create_react_agent` 的签名里有 `pre_model_hook` / `post_model_hook` / `prompt`，工具函数本身也能包装。这比原方案假设的"只有两个干净切入点"多一个：模型调用**前**也能插逻辑，所以原方案砍掉的 `on_reasoning` 其实做得了。

| 关注点 | 现在的位置 | P1 落点 | 形态 |
|---|---|---|---|
| 轮数守卫 | `post_model_hook=_tool_round_guard` | 中间件提供 `post_model_hook()` | 回调 |
| 模型调用前（预算、动态工具、脱敏） | 无 | 中间件提供 `pre_model_hook()` | 回调 |
| 工具闸门、结果脱敏、工具计时 | `_execute_http` 开头 + `_LlmTrace` | `on_acting` 包住一次工具调用 | 洋葱 |
| 熔断、用量归集 | `gateway.guarded_astream` | `on_model_call` 包住模型流 | 洋葱 |
| 系统提示装配 | `chat_service._context_from_config` 字符串拼接 | `on_system_prompt` | 变换 |
| trace 与事件观察 | `_LlmTrace` 在事件循环里手工计时 | `on_event` | 观察者 |

**不做 `on_reply`（原方案有，复核后取消）**：它包住的是 `_agent_events` 整个生成器，而这一层的 try/except/finally 已经在 `stream_chat` 里（部分内容落库、置 failed / cancelled、摘要后台刷新）。再包一层不新增能力，只会让"收尾到底谁负责"变成两个地方。总超时这种需求，直接加在 `stream_chat` 的 `asyncio.wait_for` 上更清楚。

**不做 `on_compress_context`**：摘要压缩跑在响应之后的后台线程（`schedule_summary_refresh`），不在事件循环路径上，钩不进去；要统一得先把它改成请求内任务，是另一件事。

**接口形状**（每个方法都可选；装配时扫描实例实际实现了哪些，未实现的直接跳过、不产生调用开销）：

```python
class ChatMiddleware:
    def post_model_hook(self) -> Callable | None: ...         # 交给 create_react_agent
    def pre_model_hook(self) -> Callable | None: ...          # 同上
    async def on_acting(self, call, next_): ...               # 包一次工具执行
    async def on_model_call(self, model, stream, next_): ...  # 包一次模型流
    def on_system_prompt(self, prompt: str) -> str: ...       # 变换：上一个的输出是下一个的输入
    def on_event(self, event: dict) -> None: ...              # 观察者，不允许改变事件
```

装配集中在 `_agent_events` 顶部，新增能力只加一个类：

```python
middlewares = [RoundGuardMiddleware(max_rounds), ToolPermissionMiddleware(),
               TraceMiddleware(ctx.model) if trace else None]
graph = create_react_agent(
    ctx.llm, ctx.tools, prompt=apply_system_prompt(middlewares, ctx.system_prompt),
    pre_model_hook=chain_hooks(middlewares, "pre_model_hook"),
    post_model_hook=chain_hooks(middlewares, "post_model_hook"),
)
```

**内置三个**（从现有代码迁，先搬不加能力）：`RoundGuardMiddleware`（`_tool_round_guard` 原样）、`TraceMiddleware`（`_LlmTrace` + 事件观察）、`ToolPermissionMiddleware`（P3a 的 `check` / `log_decision`）。

**实施顺序**（每步可独立验证、可单独回滚）

1. `app/services/middleware.py`：协议 + `chain_hooks` / `apply_system_prompt` + `RoundGuardMiddleware`。纯搬迁，行为不变。
2. `TraceMiddleware`：把 `_LlmTrace` 的显式调用改成 `on_event` 分发，调试面板的步骤数、顺序、字段应逐项一致。
3. `ToolPermissionMiddleware`：把 `_execute_http` 开头的 `check()` 挪进 `on_acting`。**工作流与工具页测试不经过 LangChain 工具包装**，仍要直接调 `check()`——两条路径都得留，不能只搬一半。
4. 可选：`BudgetMiddleware`（`pre_model_hook` 看累计用量，超预算把 `tool_choice` 置 none 并注入收尾提示）——等有明确成本上限需求再做。

**实施进度（2026-10-26）**

- **第 1 步已完成**：`services/middleware.py` 落地 `ChatMiddleware` 协议、`chain_hooks`、`apply_system_prompt`、`notify_event` 与 `RoundGuardMiddleware`。`ToolRoundsExceeded` 跟着搬到 middleware，`chat_runner` 改成 import **同一个类**（各留一份会让 `_finished_reason` 的 `isinstance` 判不到）。`_agent_events` 改用 middlewares 列表装配；`pre_model_hook` 暂无实现者，`chain_hooks` 返回 None、不建节点，所以行为与搬迁前一致——真实循环验证：超限仍抛同一个异常、`finished_reason=exceed_max_iters`、允许的两轮照常执行，正常场景的事件数与 seq 不变；`test_middleware` 新增 9 条。
- **第 2 步已完成**：`_LlmTrace` 整体搬到 `TraceMiddleware`，`chat_runner` 不再持有 trace 逻辑，只留 `on_chunk` / `close_call` / `tool_step` 三个调用点。**没有改成纯 `on_event` 观察者**：llm 步骤要按"模型调用 id"归组 chunk，并读那次调用的 usage，这两样只在 chunk 层（`AIMessageChunk.id` / `usage_metadata`），事件里没有；只凭事件顺序能推断步骤边界，但 usage 会丢、调试面板 token 变空，属于回归。等事件契约补上 call_id 与 usage 再切，理由写在类注释里。验证方式：同一段调试路径（工具一次 + 回答）先存 trace 基线，搬迁后对比除 `id` / 开始时间 / 耗时之外的字段，逐项一致（llm → tool → llm，含 usage 与 first_token_ms）。
- 第 3 步（闸门搬进 `on_acting`）未开始。
- **顺带发现**：`create_react_agent` 已被 langgraph 标记废弃（`LangGraphDeprecatedSinceV10`，建议迁到 `langchain.agents.create_agent`，V2.0 移除）。现在不动——对话与工作流引擎都依赖它，迁移该单独做一件事，且要先确认 `pre/post_model_hook` 在新 API 里的对应物。

**与 OP-08 合并**：`TraceMiddleware` 同时负责把 `TraceStep` 批量写 `run_nodes`（`15` 号文档 OP-08 的既定内容），一次做完，不重复动 `chat_runner`。

**验收**

- 轮数超限仍以 `exceed_max_iters` 结束、运行 failed（`test_chat_runner.py:115` 原断言不变）；
- 调用链：一轮带 2 库检索 + 1 工具的对话，`run_nodes` 出现对应步骤，顺序与耗时合理；
- 新增一个中间件的成本 = 写一个类 + 加进列表，不需要改 `_agent_events`；
- 线上首字节无回退（`test_chat_speed.py` 的口径）。

**风险**：中。抽层本身不改行为，但 `TraceMiddleware` 落在事件循环里，计时误差要接受 ±几毫秒；不要把 DB 写放进事件循环（`run_nodes` 批量写走线程池，与现有 `run_in_threadpool` 口径一致）。

### 4.4 P2 上下文 offload + 提示词分层（1 人天）

**目标**：工具结果被截断后模型能回读全文，而不是重复调用同一个工具。

**改动点**

1. 新表 `tool_result_blobs`：`id / run_id / tool_call_id / tool_name / content / char_count / created_at`，`content` 上限 256KB（超了只存前 256KB 并标 `truncated`）。
2. 落库时机：`on_acting` 收到结果时，若 `len(result) > TOOL_RESULT_STORE_CHARS` 才写 blob，正常结果不落（避免表膨胀）。
3. 新增内置工具 `read_tool_result(run_id, tool_call_id, offset=0, limit=4000)`：只允许读**本轮 run** 的结果（`run_id` 从上下文注入，不接受模型传任意值），返回切片。
4. 系统提示词分层：`on_system_prompt` 依次拼 `[base]` → `[KB 引用块]` → `[运行时提示]`，运行时提示里说明"工具结果超过 N 字被截断，可用 read_tool_result 回读"。

**验收**

- 单测：结果 10KB 的工具，下发 200 字 + `truncated=true`，模型侧能通过 `read_tool_result` 取到第 4000-8000 字；
- 单测：`read_tool_result` 传别的 `run_id` 取不到（越权 404 语义）；
- 手验：多轮工具场景下重复调用次数下降（对照 10 轮真实会话，人工看）。

**风险**：低。唯一成本是存储；`tool_result_blobs` 按 run 级联删（`ON DELETE CASCADE`）随运行记录清理。

## 6. 不做清单与理由

| 不做 | 理由 |
|---|---|
| 换 AgentScope 2.0 | 工作流编排（12 类节点、并行、人工审核）是产品核心，AgentScope 的 Pipeline/SOP 仍是 EXP；换框架等于重写编排层，收益不抵成本 |
| SSE 断点续传 | 需要服务端按 `reply_id` 缓存事件（Redis 或表），只对"网络抖动且不刷新页面"这一小撮场景生效；刷新后读 DB 已经能恢复最终态。P0 留了 `id:` 行，将来要做不必改协议 |
| 5 档权限模式矩阵 | 内部平台的调用方只有登录用户 / API Key / 分享访客三类，`DEFAULT + EXPLORE` 两档就够；`BYPASS`、`ACCEPT_EDITS` 是给本地编码 agent 设计的 |
| 工具组运行时启停（`ResetTools`） | 动态换工具集要每轮重建 `create_react_agent`，会打断流式；且当前工具规模（内置 2 + 单智能体几个 HTTP）远没到"选不准"的程度。真要治，先治"绑错工具"（P3a 的闸门） |
| HITL 工具确认 | 对话侧没有持久化 checkpointer（`MemorySaver` 只在工作流引擎里），要支持"挂起 → 确认 → 恢复"得先上 `langgraph-checkpoint-postgres`（`09-演进路线.md` 已列为待做）。在写操作类工具出现之前，投入产出不成立 |
| Agent Team / A2A | 产品形态是"单智能体 + 分享"，多智能体协作没有业务入口 |
| 事件拆成 20 类 | 前端 `switch` 与三处 transport 都要改，收益仅是"更像 AgentScope"。保留 6+2 类，加字段即可 |

## 7. 需要拍板的开放问题

1. **P0 是否接受"6 类事件 + 加字段"而不是照搬 start/delta/end？** 推荐接受：前端零改动，`seq` + `finished_reason` 已能覆盖 90% 的收益。
2. **P0 与 P1 是否合并成一次改造？** 推荐合并：都要动 `_agent_events`，分两次做等于同一段代码改两遍。
3. **P3a 的 `allowed_hosts` 默认值**：建议存量工具为空 = 放行 + WARN + 审计，给一个版本窗口补白名单，之后改为"空 = 拒绝"。需要确认能否接受这个过渡期的宽松。
4. **P2 的 `tool_result_blobs` 保留期**：建议跟随运行记录的保留策略（当前无清理任务），先不单独设 TTL；如果要设，需要和 `runs` 的清理一起定。
5. **谁验**：P0/P1 的验收里"前端行为不变"需要人在浏览器里点一遍；按 `05` 号文档的约定，交付时确认是由使用者验还是我跑自动化。
