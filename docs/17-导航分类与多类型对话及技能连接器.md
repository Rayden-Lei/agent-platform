## 0. 结论摘要

| 议题 | 结论 | 代价 | 主要风险 |
|---|---|---|---|
| **菜单分类** | 纯前端改动：`constants/nav.tsx` 加 `group` 字段 + 侧栏渲染分组标题，**不进库**。分成 6 组 17 项（现有 14 项 + 技能 + MCP 连接器 + 模型归入"能力"） | 0.5～1 人天 | 几乎为零；唯一要小心的是**空组不渲染**（caller 只能看到 2 项，分组后不能留 5 个空标题） |
| **对话分类型** | 不做三套实现，做**一个对话外壳 + 三个执行适配器**。`conversations` 加 `kind`（model / agent / workflow），路由仍是 `/chat`，靠 `?kind=` 区分 | 3～4 人天（不含工作流对话的语义改造） | **工作流对话的"多轮"语义**是唯一的真难点，见 §3.4；不先定死这个，做了也是返工 |
| **技能（Skills）** | 形态选"**渐进式披露**"：列表只把 name + description 给模型，模型需要时调 `load_skill(name)` 取正文。不是把技能全文塞进 system prompt | 2～3 人天 | 与现有「提示词模板」职责重叠，必须在 UI 上把两者说清（§4.4） |
| **MCP 连接器** | 接 MCP server 的 **tools**，同步成本地 `tools` 行（`type='mcp'`），复用现有绑定、执行闸门、审计。**首版只支持 HTTP / SSE 传输**，不接 stdio | 4～5 人天 | 连接生命周期与失败隔离；MCP 工具的参数是动态的，与现有 `tools.config.parameters` 静态声明模型要打通 |

**推荐实施顺序**：菜单分类（无依赖，先做，立刻可用）→ 对话分类型（要先拍板 §8 的 2 个问题）→ 技能 → MCP 连接器。
理由：前三者都改前端/装配层，MCP 动的是工具执行内核，放最后，前面三件做完不影响它。

## 1. 现状盘点

### 1.1 菜单

| 项 | 现状 | 位置 |
|---|---|---|
| 菜单定义 | 前端常量数组 `NAV_ITEMS`，14 项**扁平排列**，只有 `key / label / icon / roles` | `frontend/src/constants/nav.tsx:14-29` |
| 权限过滤 | `visibleNavItems(role)` 按 `roles` 过滤；caller 只剩「工作台」「对话」 | 同上 `:31` |
| 渲染 | `SideNav` 直接 `map` 出按钮列表，无分组、无小标题 | `components/layout/SideNav.tsx:36-62` |
| 标题 | `navTitle(pathname)` 最长前缀匹配，详情页显示父菜单名 | `nav.tsx:37-42` |

**判断**：菜单是纯前端常量，没有后端菜单表。这意味着"分类"可以零后端成本落地 —— 但反过来，**运营也不能在线改菜单**。当前没有这个需求，不建议为分类去建表。

### 1.2 对话

| 项 | 现状 | 位置 |
|---|---|---|
| 对话入口 | 只有一条：`POST /agents/{id}/chat`，必须绑定一个**已发布智能体** | `api/v1/chat.py:79` |
| 会话表 | `conversations` 已有 `agent_id` 与 **`workflow_id`（预留、从未写入）** 两列 | `db/models.py:209-210` |
| 会话通道 | `channel`（ui / api / share）已区分，归属判定在 `conversation_service.owns` | `models.py:214` |
| 流式契约 | 6 类事件 `citations / delta / tool_call / tool_result / done / error`，带 `seq` / `reply_id` | `services/chat_events.py`、`docs/16` §4.1 |
| 工作流执行 | `POST /workflows/{id}/run`，**入参只有一个 `input: str`**，返回整段结果（非流式、无多轮） | `api/v1/workflows.py:112`、`RunIn` |

**判断**：三件关键事实决定了方案形状 ——
1. `conversations.workflow_id` 是**预留列**（`09` §4 记着"预留字段，代码未使用"），做工作流对话不用新建表，直接启用它；
2. 工作流运行是"输入 → 输出"的**一次性函数**，没有对话状态；`MemorySaver` 只在人工审核时用；
3. 对话事件契约已经稳定且与具体执行器解耦（`StreamState` 只认事件，不认是谁产的），**这是能做适配器的前提**。

### 1.3 工具与能力层

| 项 | 现状 | 位置 |
|---|---|---|
| 工具表 | `tools`：`type`（builtin / http）、`config`（含 `parameters` JSON Schema 子集）、`auth` + `secret_enc`、`allowed_hosts` | `models.py:115-129` |
| 执行入口 | **唯一**：`execute_tool` → 中间件（闸门）→ `_dispatch` | `tools/executor.py:22` |
| 参数声明 | 静态：`config.parameters` 由人在工具页填，`build_args_model` 生成 pydantic 模型 | `tools/schema.py:79` |
| 装配 | `build_tools(tool_dbs, source, agent_id, run_id)`，内置 2 个恒有 + 启用的 http 工具 | `tools/langchain_tools.py:64` |
| 提示词 | 模板渲染进 `system_prompt` 后落库，运行时只读 `system_prompt` | `agents.prompt_template_id` |

**判断**：工具层已经是"**一个执行入口 + 一个静态参数声明**"的结构。MCP 要接进来，最省事的路径是**让 MCP 工具变成 `tools` 表里的一行**（type='mcp'），而不是另开一套执行路径 —— 否则闸门、审计、工作流工具节点、工具页测试全都要再判一遍，重演 `docs/16` P1 第 3 步刚合并掉的问题。

## 2. 议题一：菜单分类

### 2.1 方案对比

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A. 纯前端分组 | `NavItem` 加 `group`，`SideNav` 先按组分组再渲染小标题 | 0.5 人天 | **推荐（2026-11-05 已实施）** |
| B. 分组 + 可折叠 | A + 组标题点击折叠，状态存 localStorage | +0.5 人天 | 建议一起做（17 项在小屏上必须能收） |
| C. 菜单进库、运营可配 | 新表 `nav_items` + 接口 + 页面 | 3 人天 + 一个后台页 | 不做：内部平台，菜单由代码版本控制更安全（避免线上被改坏无法回滚） |
| D. 二级侧栏（父菜单点开再出子菜单） | 两级导航 | 2 人天 + 路由结构改造 | 不做：17 项不值得两级，多一次点击、移动端更难用 |

### 2.2 分组表（建议）

| 组 | 成员 | 谁可见 |
|---|---|---|
| （无标题）概览 | 工作台 | 全部 |
| **构建** | 智能体、提示词模板、工作流、知识库 | admin / developer |
| **能力** | 模型、工具、技能、MCP 连接器 | admin / developer |
| **对话** | 对话 | 全部 |
| **运营** | 运行记录、定时任务、API Key | admin / developer |
| **系统** | 用户管理、审计日志、系统参数 | admin |

设计取舍：

1. **「模型」放"能力"而不是"构建"**：模型是"接进来的外部资源"，与工具、技能、连接器同类；构建组放的是"用这些能力拼出来的东西"。
2. **「对话」单独成组且只有一项**：这是**唯一 caller 能用的功能组**。分组后 caller 看到的是「工作台」+「对话」两个组标题 + 两个菜单项，比现在"两项混在一堆里"更清楚。
3. **不按"前端/后端/安全"这类技术维度分**：使用者是业务与开发者混合，按"我在做什么事"分组比按技术层分组好理解。
4. **空组不渲染**（必须）：caller 没有构建/能力/运营/系统组，若照抄 DOM 会留 4 个空标题。过滤逻辑应是"先按角色过滤菜单项，再丢掉没有成员项的组"。

### 2.3 顺带要改的三处

1. **顶栏标题**：分组后详情页显示"构建 / 智能体"还是只有"智能体"？建议**只显示菜单名**，保持现状（`navTitle` 逻辑不变），避免顶栏变长。
2. **侧栏滚动**：`SideNav` 的 `nav` 已经是 `overflow-y-auto`，17 项 + 6 个组标题在 768px 高的屏幕上会超，滚动可解；但要确认**品牌区固定在顶部、导航区独立滚动**（现在是整块 `h-full flex-col`，品牌区不滚动 —— 已满足）。
3. **移动端抽屉**：共用同一个 `SideNav` 组件，分组自动生效，不用改。

### 2.4 不进库的理由（要说清，避免以后被推翻）

菜单是"代码的一部分"：改菜单 = 发版。好处是**权限矩阵与代码同源**（`docs/01` 第 3 节），不会出现"线上菜单被改坏了但没人知道改了什么"。真要在线配置，等出现"不同客户要不同菜单"的真实诉求再说 —— 那时该做的是**租户级功能开关**，不是把菜单表搬到库里。

## 3. 议题二：对话分类型

### 3.1 三种对话的实质差异

| 维度 | 模型对话 | 智能体对话（现状） | 工作流对话 |
|---|---|---|---|
| 谁编排 | 无编排，模型直答 | ReAct 循环（`create_react_agent`） | 工作流引擎（12 类节点，确定性） |
| 配置来源 | 模型 + 参数 | 已发布版本快照 | 工作流图（线上版本） |
| 工具/知识库 | 无 | 有（`tool_ids` / `kb_ids`） | 由节点决定（检索节点、工具节点） |
| 多轮 | 有（历史进 messages） | 有（历史 + 摘要压缩） | **无原生多轮**（见 §3.4） |
| 输出形态 | 纯流式文本 | 流式文本 + 工具事件 | 一次性结果 / 节点进度 |
| 适用场景 | 试模型、对比输出、裸能力验证 | 业务问答、带工具的任务 | 固定流程（审核、审批、多步确定性处理） |

### 3.2 关键判断：一个外壳 + 三个适配器

**不要**为三种对话各做一套页面、一套 SSE 解析、一套会话列表 —— 那是三份重复代码，且 `docs/16` 刚把事件契约统一过。

推荐结构：

```
POST /chat/stream  { kind, target_id, message, conversation_id? }
        │
        ├─ kind=agent     → chat_service.prepare_chat      （现有链路，不动）
        ├─ kind=model     → 新增 model_chat：无工具、无知识库、system_prompt 可空
        └─ kind=workflow  → 新增 workflow_chat：调 workflow_service，事件映射
        │
        └─ 统一走 EventStream（seq / reply_id）→ 同一套 SSE → 同一个 ChatPanel
```

为什么可行：`chat_events.EventStream` / `apply_event` 只认事件类型，不认来源；`ChatPanel` + `useChatStream` 只认事件，不认后端是谁。**这两层已经解耦，是白捡的架构红利**。

### 3.3 数据模型

`conversations` 加一列，其余复用：

| 列 | 变更 | 说明 |
|---|---|---|
| `kind` | **新增** `String(16) not null default 'agent'` | `model / agent / workflow`；存量会话回填 `agent` |
| `agent_id` | 已有，改语义 | 仅 `kind=agent` 非空 |
| `workflow_id` | 已有（预留） | 仅 `kind=workflow` 非空，**启用** |
| `model_id` | **新增** `BigInteger null` | 仅 `kind=model` 非空（模型对话直接指向模型行） |

约束（按"唯一性靠 DB 约束兜底"的规范）：

```sql
ALTER TABLE conversations ADD CONSTRAINT ck_conversations_kind CHECK (
  (kind = 'agent'    AND agent_id IS NOT NULL AND workflow_id IS NULL AND model_id IS NULL) OR
  (kind = 'workflow' AND workflow_id IS NOT NULL AND agent_id IS NULL AND model_id IS NULL) OR
  (kind = 'model'    AND model_id IS NOT NULL AND agent_id IS NULL AND workflow_id IS NULL)
);
```

迁移脚本：`backend/scripts/migrations/20261105_xxxxxx_conversation_kind.py`（幂等：`ADD COLUMN IF NOT EXISTS` + 回填 + 加约束前先校验存量行）。

**注意**：现有 `conversations.agent_id` 的 `ondelete` 是 `CASCADE` —— 删智能体会连带删会话。工作流对话启用 `workflow_id` 后同样 `CASCADE`（已定义），语义一致，不用改。

### 3.4 唯一的真难点：工作流对话怎么算"多轮"

工作流入参只有一个字符串 `input`，且是**一次性执行**。要做多轮，只有三条路：

| 方案 | 做法 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| **a. 历史拼进 input** | 每轮把"历史对话 + 新问题"拼成一个字符串当 `input` | 零改动，今天就能做 | 工作流内部无法区分"系统指令"与"历史"，提示词容易串味；token 随轮数线性涨 | 兜底方案 |
| **b. 工作流声明对话入口变量** | 开始节点支持声明变量 `chat_history` / `user_message`，引擎把会话历史按变量注入 | 语义干净，工作流自己决定怎么用历史 | 要改开始节点与运行入参（现在是单字符串） | **推荐** |
| **c. 不做多轮，每轮独立** | 会话只是历史展示，每轮一次独立 run | 最简单，符合工作流"确定性"本质 | 工作流看不到上下文，很多场景不可用 | 与 b 并存（b 的降级形态） |

推荐：**先做 b 的最小版**（开始节点加两个可选变量 + 运行入参改成"变量字典"，保留 `input` 作为单变量简写），c 作为不声明变量时的默认行为。

> **2026-11-05 进展**：入参已切成 `{inputs: {变量名: 值}}`（`15` 号文档 WF-04 / D-32），开始节点可声明变量、结束节点可声明输出，`GET /workflows/{id}/parameters` 供前端生成表单。也就是说 b 的地基已就绪，剩下的只是给工作流声明 `chat_history` / `user_message` 两个变量并把会话历史注入 `inputs`。a 不做 —— 拼接字符串是最容易埋坑的做法（谁拼、拼多少条、超长怎么截，全是隐式约定）。

**另一个必须定的事**：工作流的输出怎么变成"回答"。工作流输出可能是 JSON（`{status, outputs}`），而对话要的是一段文本。建议：**工作流声明一个 `reply` 输出变量**，没有就用最后一个节点的文本输出，再没有就把 JSON 格式化后展示并标"工作流结果"。这条不定，前端没法渲染。

### 3.5 事件映射（工作流 → 对话事件）

| 工作流发生的事 | 对话事件 | 备注 |
|---|---|---|
| 开始 | `done`（无内容）不算；用 `delta` 首帧占位 | 保持"先到先渲染" |
| 节点开始 | `tool_call`（`name=节点名`，`args={}`） | 复用现有工具卡片 UI，不新增事件类型 |
| 节点结束 | `tool_result`（`state=done/error`） | 失败即 `state=error` |
| 最终输出 | `delta`（一次性整段）或分块 | 工作流不是 token 流，整段下发最诚实 |
| 人工审核中断 | `done`（`finished_reason=interrupted`）+ 提示去运行详情页审批 | **首版不做对话内审批**，见 §3.6 |
| 失败 | `error` | 复用脱敏 |

**不新增 `node` 事件类型**：前端 `switch` 与三处 transport 都要改，收益只是"更准确"。复用 `tool_call/tool_result` 即可（`docs/16` §6 已就"事件不要拆细"做过同样的判断）。

### 3.6 首版明确不做

1. **对话内审批人工审核节点** —— 需要把 `Command(resume=...)` 接进对话流，且要在聊天界面渲染审批表单。先引导到运行详情页。
2. **工作流对话的取消** —— 工作流在 `asyncio.to_thread` 里跑，取消只是断开 SSE，后端仍会跑完（与现在 `POST /run` 一致）。要做真取消得给引擎加协作式中断，另一件事。
3. **模型对话的历史摘要压缩** —— 模型对话定位是"试模型"，会话短，先不做压缩；超长直接按最近 N 条截断。

> **实施记录（2026-11-05）**：上面三条与第 3.7 节的页面形态已按本文落地，另有三处细节在这里定死，避免以后各猜一套：
> 1. **节点卡片是"完成态"**：用 `graph.astream(stream_mode="updates")` 拿每个节点完成时的增量，发一对 `tool_call` + `tool_result`。引擎零改动（不必给 12 个节点工厂加进度钩子），代价是看不到转圈；要真进度得给引擎加钩子，收益只是"更实时"，暂不做。
> 2. **消息 → 入参的规则只有一处**：`workflow_chat.message_variable()`（后端）与 `Chat.tsx` 的 `readMessageVariable()`（前端）按同一套规则判断，前端据此禁用输入框并说明消息会填给哪个变量。两边各写一套会出现「前端让发、后端 400」。
> 3. **工作流对话的运行记录 `run_type=workflow`、`source=chat`**：它确实是一次工作流运行，会出现在该工作流的运行列表里，`input.inputs` 记下实际传下去的入参；模型对话的 `run_type=chat`、带 `model_id`、`agent_id` 为空，消耗按模型归集。

### 3.7 页面形态

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 单页 + `?kind=` | `/chat?kind=agent&target=3`，左侧列表按 kind 过滤，顶部一个类型切换 | **推荐**：URL 可分享、可深链，`ChatPanel` 完全复用 |
| B. 三个路由 `/chat/agent` `/chat/model` `/chat/workflow` | 各自一个页面文件 | 三份几乎相同的页面代码，不推荐 |
| C. 一个"新对话"入口弹出选类型 | 弹窗选完再进 | 每次切换要两步，高频操作变慢 |

类型切换的 UI：顶部一个分段控件（Segmented），三项「模型 / 智能体 / 工作流」；右侧"对象选择器"随类型换（模型下拉 / 智能体下拉 / 工作流下拉）。**caller 只看到「智能体」一项**（其余需要 admin/developer）。

## 4. 议题三：技能（Skills）

### 4.1 先定清楚"技能是什么"

| 概念 | 是什么 | 现状 |
|---|---|---|
| **工具（Tool）** | 模型能**做**一件事（查天气、调接口），有参数、有返回值 | 已有 `tools` 表 |
| **提示词模板（Prompt Template）** | 一段带变量的**提示词文本**，编译期渲染进 system prompt | 已有 `prompt_templates` 表 |
| **技能（Skill）** | 一套"**怎么做事**"的知识 + 可选附带资源（示例、脚本、检查清单），运行时**按需加载** | 无 |

一句话区分：工具是"手"，模板是"人设"，技能是"操作手册"。
例："报销单填写"技能 = 一页规则说明 + 一个字段对照表 + 几个正误示例；智能体平时不知道它，遇到报销问题时才调 `load_skill` 取出来。

### 4.2 三种落地形态

| 形态 | 做法 | 上下文成本 | 何时用 |
|---|---|---|---|
| **A. 全文注入 system prompt** | 绑定的技能全文拼进提示词 | 常驻，绑 3 个技能可能就几千 token | 技能短（<500 字）且每轮都用 |
| **B. 渐进式披露**（推荐） | 只把 `name + description` 放进提示词，模型需要时调 `load_skill(name)` 拿全文 | 按需，平时几乎为 0 | 技能长、技能多、命中率低 |
| C. 工具化 | 每个技能变成一个专用工具 | 同上，但工具列表会膨胀 | 不推荐：技能不是"动作"，做成工具会让模型误以为能执行 |

推荐 **B 为主，A 作为技能上的一个开关**（`always_on`）：短小的、每轮都要的规则用 A，其余用 B。这也是 Claude Skills / MCP prompts 的做法。

### 4.3 数据模型

```
skills
  id            bigint pk
  name          varchar(64)  unique          -- 模型看到的名字，英文短横线（如 expense-form）
  display_name  varchar(128)                 -- 界面显示（如「报销单填写」）
  description   text                         -- 给模型看的一句话，决定它会不会调用
  content       text                         -- Markdown 正文
  resources     jsonb                        -- 附带资源清单 [{name, type, content}]，首版只放文本
  always_on     bool default false           -- true = 全文注入 system prompt
  is_enabled    bool default true
  version       int  default 1               -- 与智能体一致：内容变则 +1
  created_by / created_at / updated_at
```

绑定：**不塞进 `agents.tool_ids`**（语义不同，工具页与执行器都会被污染）。新增 `agent_skills(agent_id, skill_id, sort)` 关联表，或复用 `agents` 的 JSONB 风格加 `skill_ids jsonb`。
推荐 **`skill_ids jsonb`**（与 `kb_ids` / `tool_ids` 一致，本项目已有两处先例，一致比规范更重要）；代价是没有外键约束 —— 与现状同级，不新增问题。

> 若将来要做"技能市场/共享"，再改成关联表。现在不做。

### 4.4 必须解决的三个边界

1. **与提示词模板的职责边界**：模板 = 智能体的"人设与输出格式"（编译期，一变就升版本）；技能 = "某类任务的额外知识"（运行时，按需）。UI 上：模板在「构建」组、技能在「能力」组；装配页两处分开（"提示词"区块选模板，"技能"区块选技能），并在技能选择器下方写一句"技能只在需要时加载，不占常驻上下文"。
2. **`load_skill` 是不是工具**：是。它是一个**内置工具**（与 `current_time` 同级），由平台提供、恒可用、不可停用。执行时从本次装配的 `skill_ids` 白名单里查 —— **必须白名单**，否则模型能读任意技能（越权）。`load_skill` 只允许读绑定的技能，传别人的 id 返回"技能不存在"。
3. **技能内容的安全面**：技能正文会进模型上下文，可能含内部地址、账号规则。与提示词模板同样口径：**接口不返回给分享访客**、审计记录"谁改了技能正文"、正文里的相对链接不外链。

## 5. 议题四：MCP 连接器

### 5.1 目标与边界

**要做的**：平台里登记外部 MCP server（HTTP/SSE），把它的 **tools** 同步进来，智能体/工作流像用普通工具一样用。
**不做的（首版）**：MCP 的 `resources`、`prompts`（prompts 用技能覆盖）、stdio 传输（需要管理子进程，服务器部署形态不匹配）、MCP 侧的 OAuth 授权流程（先用静态 Token）。

### 5.2 落地形态：MCP 工具 = `tools` 表的一行

```
mcp_servers
  id, name(unique), description
  transport       varchar(16)   -- http / sse（首版只这两种）
  url             varchar(512)
  headers         jsonb         -- 非敏感请求头
  secret_enc      text          -- Token，加密存（复用 core/security.encrypt_secret）
  is_enabled      bool
  last_synced_at  timestamp
  last_error      text
  allowed_hosts   jsonb         -- 复用工具的出站白名单判定
```

同步：`tools` 表加三列 —— `type='mcp'`、`mcp_server_id`、`remote_name`（远端工具原名，用于调用时回传）。

| 动作 | 行为 |
|---|---|
| 连接器页"同步工具" | `tools/list` → 为每个远端工具 upsert 一行 `tools`（`name` = `{server}_{remote_name}` 避免跨 server 重名；`config.parameters` = 远端 `inputSchema` 转本项目 JSON Schema 子集） |
| 绑定 | 智能体 `tool_ids` 里选它（与普通工具同列表，工具页按 `type` 打标签「MCP · 某某服务器」） |
| 执行 | `execute_tool` → 闸门 → `_dispatch` 新增分支 → `tools/call` |
| 远端工具消失 | 同步时标记 `is_enabled=false` + `last_error`，**不物理删除**（否则会破坏已有智能体的 `tool_ids` 引用） |

**为什么并入 `tools` 表而不是另开执行路径**：闸门（`allowed_hosts`）、审计、工作流工具节点、工具页"测试调用"、停用开关 —— 这五处已经围着 `execute_tool` 建好了。另开一条路径等于把这五件事各写一遍，且迟早漏一处（`docs/16` P1 第 3 步刚为这个问题把两条入口合成一条）。

### 5.3 六个必须提前定的技术点

| # | 问题 | 建议 |
|---|---|---|
| 1 | **参数声明是动态的** | 同步时把远端 `inputSchema` 落进 `tools.config.parameters`（复用现有 `ToolParameters` 子集）；不支持的 JSON Schema 特性（`oneOf`、嵌套对象）**降级为"自由对象"参数**并在工具页标黄提示 |
| 2 | **会话生命周期** | 每次调用新建连接（HTTP 无状态），**不做长连接池**：MCP 的 SSE 会话需要 `initialize` 握手，池化会引入超时与重连状态机，首版不值得。代价是每次多一次握手 RTT |
| 3 | **超时与失败隔离** | 复用 `tools.timeout`（默认 30s）；远端不可达 → `{"error": "MCP 服务器不可达"}` 回给模型（不抛异常，否则整轮对话失败） |
| 4 | **SSRF** | `url` 必须命中 `mcp_servers.allowed_hosts`（与工具同一套判定），且**禁止 `localhost` / `169.254.*` / 内网段**（除非管理员显式加白） |
| 5 | **凭据** | 走 `secret_enc`，接口永不回传明文（与 `tools.auth` 同一口径）；日志里 `Authorization` 打码 |
| 6 | **谁能用** | `mcp_servers` 只有 admin 能增删改；developer 能绑定已启用的 server 的工具；分享访客默认**不装配 MCP 工具**（与 `allow_http_tools` 同级开关） |

### 5.4 与技能的关系

MCP 也能提供 `prompts`（预设提示词）。**首版不接**：技能的渐进式披露已经覆盖同一需求，且技能的编辑体验（Markdown + 版本）比 MCP prompts 更适合非技术使用者。将来若要接，把远端 prompt 同步成 `skills` 行即可（`always_on=false`，来源标 MCP）。

- P1 无依赖、零风险、立刻改善可用性，先做；

- P5 动工具执行内核，放最后，且它天然依赖 P4 的"能力"页面骨架。

**建议合并发布**：P2 + P3 一批（对话），P4 + P5 一批（能力）。P1 单独先发。

## 8. 必须先拍板的 6 个问题

1. **菜单分组是否就用 §2.2 那 6 组？** 特别是「模型」归"能力"还是"构建"，「对话」单独成组是否可接受。
2. **"模型对话"的真实用途是什么？** 若只是"试模型/对比输出"，它可以是**运维工具**（放"能力"组下的一个入口，而不是与智能体对话并列的主对话类型）；若是业务要用的（比如给业务人员直接选模型问答），才值得做成主类型。**这决定 P2 的页面形态**。
3. **工作流对话的"多轮"按 §3.4 方案 b（开始节点声明 `chat_history` 变量）做，还是先只做 c（每轮独立、会话只做历史展示）？** 选 b 要多改开始节点与运行入参（约 +1 人天），但语义干净。
4. **工作流的"回答"怎么取？** 建议约定一个 `reply` 输出变量（没有则取最后一个文本输出）。要不要强制工作流声明？
5. **技能与提示词模板的边界是否认可 §4.1 的划分？** 若认可，装配页要拆成"提示词（模板）"与"技能"两个区块，智能体快照要加 `skill_ids`（**会影响已发布版本的快照结构**，需要一次性迁移）。
6. **MCP 首版是否接受"只支持 HTTP/SSE、不做 stdio、不做 OAuth"？** 以及"每次调用新建连接"的性能取舍是否可接受。

## 9. 风险与不做清单

### 9.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 对话分类型把 `chat_service` 拆散 | 现有智能体对话回归 | 新类型**新增分支**，不改 `prepare_chat`；用现有 `test_chat_runner` / `test_agent_debug` / `test_shares` 做回归基线 |
| 工作流对话的取消是"假取消" | 用户点停止但后端仍跑完、仍计费 | 首版在 UI 上明说"工作流运行不支持中途停止"；真取消另立一项 |
| MCP 远端工具参数超出现有 schema 子集 | 模型传参失败 | 降级为自由对象 + 工具页标黄；不同步"必填"以外的约束 |
| 技能正文进上下文导致提示词注入 | 泄露内部信息 | 技能正文与提示词同口径（不返回给访客）；`load_skill` 只读白名单 |
| `skill_ids` 进快照导致存量版本结构变化 | 旧版本回滚报错 | 快照读取用 `snap.get("skill_ids", [])` 的**一次性迁移**（迁移脚本回填空数组），不留运行时兜底 |

### 9.2 明确不做（与 `15` / `16` 的"不做清单"一致）

| 不做 | 理由 |
|---|---|
| 对话内审批人工审核节点 | 需要把 `Command(resume)` 接进对话流 + 聊天界面渲染表单，是独立工程 |
| 工作流的真取消 | 引擎在 `to_thread` 里跑，需要协作式中断 |
| 多智能体协作对话（Agent Team / A2A） | `docs/16` §6 已判定不做 |
| MCP resources / prompts / stdio / OAuth | 首版范围控制，技能已覆盖 prompts |
| 菜单进库、运营可配 | 内部平台，代码版本控制更安全 |
| 技能市场 / 跨用户共享 | 没有真实诉求 |
