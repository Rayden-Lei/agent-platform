# 智枢·智能体平台 架构设计（ADD）

版本 V2.3 · 2026-09-06 · 与代码现状同步

> 本文档描述平台"怎么做"：分层、模块、核心链路与关键设计决策。
> 改动涉及分层、核心链路或设计决策时，同批更新本文档。

## 1. 设计目标与原则

- **单体优先，内部模块化**：一个 FastAPI 进程承载全部应用模块，靠目录与依赖方向划分边界，不拆微服务。
- **数据库是唯一配置源**：模型、智能体、工具、知识库、工作流的配置全部落库，运行时不读文件配置；环境变量只放部署相关的连接信息与密钥。
- **不重复造轮子**：模型接入用 LangChain，智能体循环用 LangGraph 预置 ReAct，工作流用 LangGraph StateGraph，向量用 pgvector，调度用 APScheduler。
- **异步解耦**：文档处理走后台任务，定时任务走调度线程，工作流同步执行但放线程池，不阻塞事件循环。
- **安全内建**：密码哈希、密钥加密、JWT、登录限流、操作审计、检索权限过滤。
- **错误可见**：异常要么转成业务错误返回，要么写日志并落到运行记录，不允许静默吞掉。

## 2. 总体架构

### 2.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层   React 控制台（Vite 开发 / Nginx 静态）  REST API  SSE   │
├──────────────────────────────────────────────────────────────┤
│ 应用层   api/v1 路由 → services 业务                            │
│          认证 用户 模型 智能体 对话 会话 工具 知识库 工作流         │
│          运行记录 审计 API Key 定时任务                          │
├──────────────────────────────────────────────────────────────┤
│ 能力层   model_gateway 模型网关 │ rag 检索管道 │ workflow 引擎    │
│          tools 工具执行器 │ core 安全/鉴权/审计/调度器            │
├──────────────────────────────────────────────────────────────┤
│ 数据层   PostgreSQL + pgvector │ Redis（登录限流） │ MinIO（文档） │
└──────────────────────────────────────────────────────────────┘
```

依赖方向自上而下单向：路由只依赖服务，服务依赖能力层与数据层，能力层不反向依赖服务层。
唯一例外是 `core/scheduler.py` 依赖 `services/workflow_service.py`，因为定时触发必须与接口触发走同一条执行路径；这是有意为之，不要再新增反向依赖。

### 2.2 部署拓扑

两种形态，见 `08-运行与部署.md`：

- **Docker Compose**：api、web（Nginx 静态 + 反代 /api）、postgres（pgvector 镜像）、redis、minio 五个容器。
- **裸机进程**：uvicorn 直接跑后端，PostgreSQL / Redis / MinIO 作为外部服务；前端本地 Vite 开发或构建后由任意静态服务器托管。

## 4. 核心链路

### 4.1 认证与鉴权

1. `POST /auth/login`：来源 IP 每分钟限流（`core/rate_limiter`）→ Redis 计数检查是否锁定 → bcrypt 校验 → 是否停用 → 清计数、写审计、签发 JWT（payload：`sub` 用户 ID、`role`、`exp`）。
2. 每个受保护路由通过 `Depends(get_current_user)` 解析 Bearer 并查库确认用户存在且启用，再按用户每分钟限流（先鉴权后计数，无效 token 不占额度）；需要角色时用 `Depends(require_roles("admin", "developer"))`。
3. 前端把 token 放 localStorage，axios 拦截器注入；收到 401 清空并跳登录。
4. API Key 与 JWT 共用 Bearer 头：`get_current_user` 按 `ak_` 前缀分流到 `api_key_service.authenticate`（Key 有效 → 账号可用 → 来源白名单 → 限流 → 原子扣配额），鉴权来源记在 `request.state.auth_via`；`require_roles` 默认拒绝 API Key，执行类接口显式 `allow_api_key=True` 开放。
5. 限流结果挂在 `request.state.rate_limit`，请求 ID 中间件据此回写 `X-RateLimit-*`；超限由 `rate_limiter.limit_exceeded` 生成带 `Retry-After` 的 `BizError(429)`，三个维度共用同一出口。

### 4.2 对话

```
客户端 ──POST /agents/{id}/chat──▶ 路由
  0 运行时只读 agents.system_prompt：绑定了 Prompt 模板的智能体在保存时已把渲染结果写进这一列（FR-028），对话链路不感知模板
  1 prepare_chat：校验已发布 → 取/建会话 → 落用户消息 → create_run(started_at)
  2 build_chat_context：
      build_llm(模型配置) → build_tools(内置 + 该智能体的 HTTP 工具)
      若绑定知识库：_queries_for（默认只用原问题；RAG_QUERY_REWRITE_ENABLED 时让 LLM 改写 3 个子查询，3s 超时）
        → _retrieve_all：每个 (知识库, 查询) 并行 retrieve_with_stats(带角色)
        → 按 (kb_id, chunk_id) 合并取最高分 → 截断到 RAG_TOP_K × 知识库数 → 拼【参考片段】进 system prompt
      历史：最近 CHAT_HISTORY_MAX_MESSAGES 条原文；更早的折叠进会话上持久化的摘要（conversations.summary）作为 SystemMessage，
        未折叠的攒够 CHAT_SUMMARY_BATCH_MESSAGES 条时本轮注入截断原文并标记 summary_pending，路由在 done 之后用后台线程
        refresh_conversation_summary 把旧摘要与它们压成新摘要并落库（不占首字节）；不足一批按原文注入
      以上同步阶段都经 run_in_threadpool 执行，不阻塞事件循环；build_llm 按 default_params.thinking 透传 extra_body 关闭 / 开启思考模式，并按 (模型 id, updated_at) 缓存 ChatOpenAI 实例复用 httpx 连接池（改配置自动换新实例）
  3 写审计 rag_retrieve（召回 chunk_id、鉴权剔除数）
  4 create_react_agent(llm, tools, prompt).astream(stream_mode="messages")
      AIMessageChunk.content → delta 事件
      tool_call_chunks 累积参数 → 工具执行后 ToolMessage → tool_call + tool_result 事件
      usage_metadata → 累计 token
  5 保存 assistant 消息（内容、引用、工具调用、token）→ finalize_run(success) → done 事件
  异常 → finalize_run(failed) → error 事件
  客户端中断 → finally 里 finalize_cancelled_chat：部分内容落库、运行 cancelled
```

SSE 事件契约见 `04-接口设计.md` 第 5 节。

### 4.3 RAG 管道

**入库**（`rag/pipeline.process_document`，后台任务）：

1. 从 MinIO 下载到临时目录 → `parser.parse_document` 按扩展名解析成片段列表 `[{content, meta}]`。
2. `chunk_segments` 按类型分片：Markdown 用标题分割器，表格每行一片（超过 `chunk_size` 的行按字段边界再切，每片以首列作行标识，单个超长字段用分片器切并标「(续)」，`meta.part` 记序号），其余用中文分隔符优先的递归字符分割器，`chunk_size / chunk_overlap` 取知识库配置。
3. `embed_texts_detailed` 批量向量化：配置了 `EMBEDDING_API_KEY` 走 OpenAI 兼容接口（每批 20 条，透传 `dimensions`），未配置或调用失败退化为 hash 向量（词与二元组哈希后归一化）并打 WARN，返回值同时带回实际使用的后端。入库按 `INGEST_BATCH_SIZE`（100）逐批向量化并提交，`chunk_count` 随批推进（列表页可见进度），中途失败已提交的批保留、文档置 failed，重新解析时整体清掉重来。
4. 写 `document_chunks`，`meta` 里冗余写入知识库权限快照（`kb_id / doc_id / is_public / visible_roles / policy_version`）供检索过滤与审计，以及本批实际使用的向量后端（`embedding_mode / embedding_model / embedding_dim`）供事后重建。
5. 文档状态 `ready`，`chunk_count` 更新；任一步失败置 `failed` 并记录 `error`。

**检索**（`rag/retriever`）：

1. 权限条件 `_acl_condition(role)`：admin 不过滤；其他角色只取 `meta.is_public` 为真或 `visible_roles` 含该角色的切片（无标签的存量切片视为公开）。
2. 向量召回：cosine 距离排序取 `top_k × 3`，记录向量排名。
3. 关键词召回：`extract_keywords` 取英文词与中文片段（≤ 4 字整段、更长的切三元组，最多 12 个），每个关键词并发 `ILIKE` 查询取 `top_k × 2`（走 `pg_trgm` GIN 索引，2026-09-06 起；二元组走不了索引，4 万切片时 12 个词要 2.5 秒），按命中关键词数排名。向量召回走 HNSW 索引，候选行不加载 embedding 列。重排后内容完全相同的切片只保留最高分一条（同一药品多个批准文号的重复行）。评测接口 `stats.timings` 给出向量化 / 向量召回 / 关键词召回 / 重排各段毫秒数。
   重排：配置了 `RERANK_PROVIDER` 时取 RRF 前 `RERANK_CANDIDATES` 条请求重排服务（`rag/rerank.rerank_by_model`，cohere / dashscope 两种请求体），`score` 取 `relevance_score`，淘汰阈值改用 `RERANK_MIN_SCORE / RERANK_GAP_RATIO`；失败或超时退回词法重排并记 `_last_failure`（`/system/status.rerank`，进 `degraded`）；结果带 `rerank_mode / rerank_score`。
4. RRF 融合：`score = Σ 1 / (60 + rank)`。
5. `rerank` 词法重排：关键词覆盖率与命中长度加权，与 RRF 分各占一半。
6. `_prune` 淘汰：低于 0.01 或不到榜首 35% 的丢弃。
7. `_authorize` 逐条再鉴权（第二道闸门），返回前 `top_k` 条完整切片文本。

**权限模型**：知识库级 `is_public / visible_roles / policy_version`，切片级冗余标签；权限变更只改知识库表并递增 `policy_version`，存量切片标签不回写（检索第一道闸门看的是切片标签，因此改权限后要重新处理文档才对存量生效，这是已知局限）。

### 4.4 工作流引擎

**图结构**（存 `workflows.graph`）：

```json
{
  "nodes": [{"id": "node_1", "type": "agent", "config": {...}, "position": {"x": 0, "y": 0}}],
  "edges": [{"from": "node_1", "to": "node_2", "when": "true"}]
}
```

**状态**（`WorkflowState`）：`input` 初始输入、`output` 最近一个节点的输出、`condition_result`、`loop_index`、`review_result`、`node_outputs` 各节点输出字典、`steps` 执行轨迹。`steps`、`node_outputs`、`output` 三个键带 reducer（追加 / 合并 / 取最后一次写入），节点只返回增量；这是同一超步多个节点写同一键（并行分支）的前提，串行图下结果与整体覆盖相同。`start / end` 节点返回空增量。

**节点**（`engine.NODE_BUILDERS`）：

| 类型 | 配置 | 行为 |
|---|---|---|
| start / end | 无 | 只写节点日志 |
| agent | `agent_id`，可选 `prompt` 覆盖 | 用该智能体的模型与提示词做一次非流式调用 |
| tool | `tool_name`，可选 `args` 固定参数 | 无固定参数时把输入当 JSON 解析为参数 |
| condition | `expression` | 受限命名空间 `eval`，可用 `input / output / loop_index / review_result` 与少量内置函数；结果进 `condition_result` |
| kb_retrieval | `kb_id`、`top_k` | 以触发者角色检索，输出切片列表 |
| code | `code` | `exec` 执行 Python，读 `input`，把结果赋给 `result`；**无沙箱** |
| http | `url`、`method` | GET 传 `params={"input": ...}`，POST 传 `json={"input": ...}`，30 秒超时 |
| loop | `count` 或 `expression` | 递增 `loop_index`；出边 `when=loop` 回环、`when=exit` 退出 |
| human_review | `instruction` | `interrupt()` 暂停，等待 resume 传入决定 |
| parallel | 无 | 扇出：输入透传为输出，出边 ≥ 2 条各开一条分支，分支在同一超步并发执行 |
| join | 可选 `output_field` | 汇聚：等全部分支完成后把各分支末节点的输出收集成 `{末节点 id: 输出}`，覆盖 `output` |

通用配置：`input_ref` 指定输入来源（`{{input}}`、`{{output}}`、`{{node_id}}`、`{{node_id.a.b}}`），缺省取上一节点输出；`output_field` 按点路径从输出中提取字段。

**并行分支**（FR-029）：分支是线性链，只允许 `agent / tool / kb_retrieval / code / http`；链尾必须连到同一个 `join`。分支内节点缺省输入不再是 `output`（同一超步多个分支同时写、取值不确定），而是编译期算出的前驱：首节点取 `parallel` 的输出，其余取本分支上一节点（`validation.branch_predecessors`）；分支内 `input_ref` 不允许 `{{output}}`。`steps` 里两条分支的条目顺序不保证，只保证集合完整。任一分支失败整条运行 failed，已完成的另一分支节点日志保留 success。结构规则由 `workflow/validation.validate_graph` 检查（六条，见 `11` 4.5.3），保存、编辑器测试运行、正式运行前在服务层显式调用返回 400，`build_workflow` 内再兜底一次（定时任务路径按 failed 落库）。

**连线**：普通节点直连；条件节点按 `when` 为 `true / false` 走条件边；循环节点按 `loop / exit` 走条件边；`parallel` 的出边不带 `when`，逐条直连即并发；`join` 的入边用 LangGraph 列表边一次连入，等全部前驱完成才执行。

**执行**（`workflow_service.execute_workflow`）：`build_workflow` 编译（绑定进程内 `MemorySaver` checkpointer）→ `graph.invoke(payload, thread_id=run.id)`。三个入口共用：接口触发放 `asyncio.to_thread`，人工审核续跑传 `Command(resume=decision)`，定时任务在调度线程直接调用。结果：正常结束 `finalize_run(success)`；遇到 `interrupt` 置 `awaiting_review` 并保存中断信息；异常 `finalize_run(failed)`。每个节点开始与结束各写一条 `run_nodes`。

编辑器内的测试运行走 `test_run_workflow`：随机 `thread_id`，不落 `runs`。

### 4.5 工具

- 数据库 `tools` 表：`type` 为 `builtin` 或 `http`；`config` 对 HTTP 工具存 `url / method / headers / parameters`（参数声明，JSON Schema 子集，见 `03` 4.2）；`timeout` 秒。
- `tools/schema.py`：参数声明的校验、按声明生成 pydantic 参数模型、调用前校验与规范化（`check_tool_args`）。对话、测试接口、工作流 `tool` 节点共用。
- `tools/executor.execute_tool`：内置工具按名字分发（`current_time`、`calculator`），HTTP 工具用 httpx 调用（GET 参数走 query，其余走 JSON body），返回 JSON 或 `{"result": 文本}`，失败返回 `{"error": ...}` 不抛出。
- `tools/langchain_tools.build_tools`：智能体对话时总是带上两个内置工具，再把该智能体绑定的 HTTP 工具包装成 `StructuredTool`，`args_schema` 由参数声明生成，模型按结构化参数调用；未声明参数的工具暴露为无参数工具。模型传参不符合声明时校验错误作为工具结果回给模型（`handle_validation_error`），不中断对话。

### 4.6 定时调度

`core/scheduler`：进程内 `BackgroundScheduler`，启动时从 `scheduled_jobs` 加载启用的任务；创建、启停、删除任务时同步增删调度器里的 job。触发时走 `execute_workflow`，运行记录 `input.scheduled = true`，更新 `last_run_at`。

### 4.7 运行记录生命周期

```
create_run ── running ──┬── success   （finished_at, latency_ms）
   (started_at)         ├── failed    （error, finished_at, latency_ms）
                        ├── cancelled （对话被客户端中断；部分内容落库）
                        └── awaiting_review ──resume──▶ success / failed
```

- 所有产生运行记录的入口必须走 `run_service.create_run / finalize_run`；收尾幂等，终态不会被二次覆盖。
- 成本在收尾时按当时模型单价折算写入 `runs.cost`（2026-09-06 起；之前是读取时折算不落库），之后改单价不追溯；按模型聚合用 `runs.model_id` 快照，智能体换模型后旧运行仍归旧模型。

### 4.8 审计

`core/audit.record_audit`：登录成功/失败、模型创建/删除、智能体发布、对话检索。写入 `audit_logs`，用户被删除时保留记录（外键 `SET NULL`）。

### 4.9 可观测性与降级

```
请求 → RequestContextMiddleware（分配/沿用 X-Request-Id，解析客户端 IP，写 contextvar 与 scope）
     → CORSMiddleware（按 CORS_ORIGINS 白名单）
     → IpFilterMiddleware（命中 IP_DENYLIST 直接 403，带跨域头与 trace_id；/health 豁免）
     → 业务处理（所有日志自动带 [request_id]；审计自动带来源 IP）
     → 响应（头 X-Request-Id；错误体带 trace_id）
     → 访问日志：方法 路径 状态码 耗时
```

- 日志格式 `时间 级别 [request_id] logger: 消息`；无请求上下文时为 `-`（启动、调度线程、线程池）。
- 客户端 IP 默认取连接对端；`TRUSTED_PROXY_ENABLED` 打开时才信任 `X-Real-IP` / `X-Forwarded-For`，且只接受合法 IP 字面量，非法值回退到对端。
- 依赖 Redis 的限流共用 `core/redis_client`：Redis 不可用则放行，故障原因经 `/system/status` 暴露，恢复时打 INFO。
- 模型调用熔断（`model_gateway/breaker`）：所有模型调用经 `gateway.guarded_invoke / guarded_ainvoke / guarded_astream` 包装，按模型连续失败计数；打开期直接 `BizError(503)` 不请求上游，到期放行一个探测（锁内原子）。流式调用以首个 chunk 为成功；摘要与查询改写在打开期走既有降级不报 503 但计入失败；连通测试以探测模式绕过打开期，成功即恢复。打开 WARN、关闭 INFO，`status()` 接进系统状态。
- 三类异常出口：`BizError` 记 INFO 按原状态码返回；`HTTPException` 保持 `{"detail"}` 并补 `trace_id`；其他异常记完整堆栈、对外只给固定文案与 `trace_id`。
- 中间件是纯 ASGI 实现而不是 `BaseHTTPMiddleware`：后者会重新包装响应体，影响 SSE 流式与客户端中断时的收尾逻辑。
- 降级状态集中在 `services/system_service.get_system_status`：向量后端、登录限流、入口限流、数据库、调度器注册数，`degraded` 汇总当前所有降级项，前端 `DegradedBanner` 在顶栏下统一提示，知识库 / 模型 / 定时任务页再读各自的局部状态。入口限流"配置关闭"不算降级，"配置打开但 Redis 故障"才算。

## 5. 关键设计决策与取舍

| 决策 | 原因 | 代价 / 局限 |
|---|---|---|
| 工作流统一同步 `invoke` + 线程池 | 节点内部有同步 DB 操作与 `asyncio.run` 调用工具，混用异步图会在事件循环里阻塞 | 每次执行占一个线程 |
| checkpointer 用进程内 `MemorySaver` | 内部使用场景审核间隔短，先不引入外部存储 | 后端重启后 `awaiting_review` 的运行无法续跑 |
| embedding 失败退化 hash 向量 | 保证入库与检索不中断 | 检索质量只剩词面匹配。2026-09-04 起不再静默：降级打 WARN、`/system/status` 与 `/health` 报模式、切片 `meta` 记录入库时用的后端、知识库页顶部告警 |
| 向量维度是全局配置 `EMBEDDING_DIM` | pgvector 列定长 | 换向量模型需要改列并重建全部切片 |
| 对话摘要按批折叠并持久化到会话 | 每轮重算的输入随会话线性增长；改为攒够一批（默认 10 条）才调一次模型，输入有界（旧摘要 + 一批消息）；2026-09-06 起该调用在响应后的后台线程执行 | 摘要最多落后一批消息，它们按原文注入、token 略多；同一会话并发触发时后写覆盖，不加锁 |
| RAG 查询改写默认关闭 | 改写要多等一次完整模型调用（DeepSeek 类实测 4～9 秒），对短问句召回收益有限 | 召回面变窄；需要时 `RAG_QUERY_REWRITE_ENABLED` 打开，超时 3 秒 |
| 响应不套统一信封 | 前端直接拿数据，FastAPI 校验错误格式天然是 `{"detail"}` | 列表分页时需要引入 `{items, total, ...}` 结构，见接口文档 |
| 代码执行节点无沙箱 | 内部可信用户 | 不能对外开放工作流编辑权限 |
| 下拉选项取分页第一页最多 100 条 | 不为选项再开一套无界接口 | 超过 100 项时要改为服务端搜索 |
| 模型 SDK 重试归零（`MODEL_MAX_RETRIES=0`） | 不设时 SDK 默认重试 2 次，超时类故障一次"失败"要等 3 × 120 秒；故障处理统一交给熔断器 | 单次网络抖动直接失败；靠熔断只计连续失败与对话页"重新生成"兜底，可按环境调回 |
| 模型熔断状态存进程内存 | 单实例部署，不为它引入 Redis 状态机 | 多实例各自熔断；连通测试只恢复当前实例 |
| 熔断只计连接 / 超时 / 429 / 5xx，4xx 不计 | 配置与参数错误不会因为等待而恢复，熔断会掩盖真正原因 | 上游持续 401 时每次仍会真实请求一次 |
