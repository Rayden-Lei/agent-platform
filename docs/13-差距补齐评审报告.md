## 2. PRD 评审发现

### 2.1 P0：开工前必须修订

**P-1 FR-027 熔断器没有考虑 SDK 默认重试，"快速失败"达不到**

- 证据：`app/model_gateway/gateway.py` 的 `build_llm` 只设了 `timeout=settings.MODEL_HTTP_TIMEOUT`，没有设 `max_retries`。`langchain_openai/chat_models/base.py:838` 声明 `max_retries: int | None = None`，为 None 时不传给客户端，落到 `openai/_constants.py:8` 的 `DEFAULT_MAX_RETRIES = 2`。
- 影响：超时类故障下一次"失败"实际是 3 次尝试，最长 3 × 120 秒；连续 5 次失败才打开熔断，串行场景要 30 分钟。PRD 第 1 节的目标"上游模型故障时能快速失败而不是拖满 120 秒超时"在现有配置下不成立，且 PRD 4.3"现状"里写的"每个请求都要等满超时才失败"低估了实际等待。
- 修订：FR-027 契约增加一条："`build_llm` 显式设置 `max_retries=0`（或新增配置 `MODEL_MAX_RETRIES`，默认 0），故障处理统一交给熔断器，SDK 层不再自行重试。"AC-013 增加断言"单次失败耗时不超过 1 个 `MODEL_HTTP_TIMEOUT`"。同时把"`MODEL_HTTP_TIMEOUT` 默认 120 秒是否下调"列为评审决策点（见第 6 节）。

**P-2 developer 修改 API Key 的权限口径三方冲突**

- 证据：
  1. PRD 第 3 节：developer 可修改"仅本人创建的 Key"；4.2 契约：`PUT /api-keys/{id}` developer 不属于本人 → 404。
  2. 前端 `src/components/AppLayout.tsx:47`：API Key 菜单只在 `user?.role === 'admin'` 时渲染，developer 进不了这个页面。
  3. 后端 `app/services/api_key_service.py`：`list_api_keys` 不按用户过滤（docstring 写"当前用户的"，实际返回全部）；`toggle_api_key`、`delete_api_key` 没有归属校验。developer 今天就能停用和删除别人的 Key。
- 影响：只给 PUT 加归属校验会造成"能删不能改"的权限面；前端不改菜单，PRD 前端章节的"新增编辑入口"对 developer 是空话。PRD 第 8 节开放问题 1 只问了 list，没覆盖 toggle / delete 和前端菜单。
- 修订：评审会定一个口径并写进 PRD 第 3 节与 4.2 契约，二选一：
  - A（推荐）：API Key 按归属隔离。list / PUT / toggle / delete 对 developer 都按 `user_id` 过滤，admin 看全部；前端菜单对 developer 开放 API Key 页。这与 `01` 第 3 节"developer 管理 API Key"的说法一致。
  - B：API Key 是 AD 共管资源，不做行级隔离，PUT 也不校验归属；PRD 第 3 节的"仅本人创建"删掉。
  无论选哪个，计划 1.2 的改动清单要同步（A 多 3 个函数、1 个菜单改动、约 0.5 人日）。

**P-3 400 与 422 的分界不一致**

- 证据：`04-接口设计.md` 2.2 规定 422 = 请求体校验失败（FastAPI 自动生成）、400 = 业务前置条件不满足。对照 PRD：
  - FR-030："最多 20 个……保存时校验，违反 → 400"；计划 2.2 用例却是"属性超过20个返回422"。
  - FR-028："变量超过 30 个 → 422"，同一节"未声明变量 → 400"。
  - FR-025："负数或超过 10000 → 422"；FR-026："非法 CIDR → 400"，"列表长度上限 50"没写状态码。
- 影响：前端与调用方无法预知同一类错误是数组还是字符串；用例写错状态码会在实现时来回改。
- 修订：PRD 第 4 节开头加一条通用规则："结构、类型、范围、数量类校验由 pydantic schema 承担 → 422；需要读库或需要跨字段语义判断的校验在服务层 → 400。"然后逐条对齐：FR-030 数量上限 → 422，`required` 子集与 `type` 白名单可以放 schema → 422（或明确放服务层 → 400，二选一写死）；FR-026 CIDR 合法性用 `ipaddress` 在 schema validator 里做 → 422，或放服务层 → 400，写死一种；FR-026 列表上限 50 → 422。计划里的用例状态码随之改。

**P-4 并行超步内 `steps` 顺序与 `output` 终值不确定**

- 证据：PRD 4.5.4 规定 `steps` 用列表追加、`output` 用"取最后一次写入"。LangGraph 同步执行时同一超步的节点由 `langgraph/pregel/_executor.py` 的线程池并发跑，完成顺序不确定，reducer 的应用顺序随之不确定。
- 影响：
  1. 并行图的 `steps` 里两条分支的条目顺序每次可能不同。计划 2.5 的用例和第 5 节"steps 逐字相同"的基线如果按精确顺序断言会随机失败；运行记录页展示也会"跳"。
  2. 并行超步结束时 `state.output` 是哪个分支的输出是随机的。PRD 已经让分支内节点不读 `output`，但没写 `join` 节点要覆盖 `output`，也没写 `join` 之后的节点默认输入是什么。
- 修订：4.5.4 加两句："并行分支的 `steps` 条目顺序不保证，只保证集合完整；`join` 节点执行后 `output` 被覆盖为汇聚字典，`join` 之后的节点默认输入即该字典。"AC-015 的"汇聚输出含两个键"改为集合断言；计划 2.5 用例注明"steps 用集合比较"。

### 2.2 P1：应修订

**P-5 FR-027 三处调用点里两处会吞掉熔断异常**

- 证据：`app/services/chat_service.py` 的 `_summarize_history`（第 43 行起）与 `_rewrite_queries`（第 74 行起）都 `except Exception` 后降级（截断 / 原查询）。熔断器在这两处抛出的 503 会被吞掉，`record_failure` 也不会被调用；连续失败计数只会来自主对话流。
- 修订：PRD 4.3 写明："摘要与查询改写在熔断打开期间直接走既有降级路径，不对外报 503；这两处的调用失败同样计入连续失败。"计划 1.4 改动清单对应加"在两个 except 分支里调用 `record_failure`"，测试加"改写超时计入熔断计数"。

**P-6 FR-028 "重新保存"即生效，与"发布"的关系要写明**

- 证据：`chat_service.get_published_agent` 直接返回 `agents` 行，对话读的是 `agents.system_prompt` 而非版本快照；`publish_agent` 只是写快照。PRD 第 3 节场景写"重新保存并发布"，AC-014 写"对话使用的仍是绑定时渲染的 system_prompt"。
- 影响：验收时会争论"PUT 之后没发布为什么对话已经变了"。这是既有行为，不是本批引入。
- 修订：4.4.3 加一句："重新保存（PUT）后 `system_prompt` 立即更新，对话随之生效，与现有智能体编辑行为一致；发布只影响版本快照。"场景里的"并发布"删掉或改为"（发布仅为留快照）"。

**P-7 FR-030 迁移脚本与真实行为变化的时间点**

- 证据：PRD 4.6 规定"未声明 `parameters` 或 `properties` 为空的工具按无参数工具暴露"，这意味着 2.2 后端合入的那一刻存量 HTTP 工具就变成无参工具，回填脚本（2.3）只是把隐式状态显式化并打印清单，不改变运行时行为。
- 修订：PRD 4.6 写明"回填脚本不改变运行时行为，漏跑不影响功能，只影响'未声明参数'标签与清单"；第 8 节风险表把"升级后变为无参数工具"的触发点从"迁移后"改为"FR-030 后端上线时"，并加一条上线前动作："上线前把受影响工具清单（可用一条 SQL 先查）发给使用方。"

**P-8 FR-026 黑名单 403 不带 CORS 头**

- 证据：`app/main.py` 先 `add_middleware(CORSMiddleware)` 再 `add_middleware(RequestContextMiddleware)`，Starlette 后加的在外层，所以请求 ID 中间件在 CORS 之外。计划 1.1 把黑名单检查放进请求 ID 中间件，其 403 响应不会经过 CORS 处理。
- 影响：浏览器直连场景下黑名单命中表现为"网络错误"而不是可读的 403；对脚本 / 服务端调用方无影响。
- 修订：二选一并写进 PRD：接受该行为并注明；或计划 1.1 把黑名单做成独立中间件，注册在 CORS 之前（内层）。

**P-9 FR-027 半开态并发缺负向用例**

- PRD 写"放行一个探测请求"，对话路径是 async 路由 + 线程混跑，需要原子地只放一个。边界用例里没有"半开时并发 2 个请求只放行 1 个、另一个 503"。补上。

**P-10 FR-028 模板名唯一与 FR-033 的关系**

- PRD 4.4 表定义 `prompt_templates.name` 全局唯一；4.9.2 让该表带 `tenant_id`，但没说唯一约束要改为 `(tenant_id, name)`。补进 4.9.4 迁移清单，或在 FR-028 建表时就用联合唯一（`tenant_id` 未触发前恒为 1）。同理 `tenants.code` 与 `users.username` 的唯一范围也要在 4.9.2 写明。

### 2.3 P2：建议

## 3. 开发计划评审发现

### 3.1 P0

**D-1 2.4 的回归基线不存在**

- 证据：`backend/tests/test_workflows.py` 只有 1 个用例 `test_workflow_crud_and_run`，图是 start→end，不产生任何有意义的 `steps`，也不覆盖条件、循环、人工审核、`input_ref`、`output_field`、`node_outputs`。计划第 5 节把"2.4 提交前后 `steps` 逐字相同"作为通过标准，第 4 节 2.4 写"`tests/test_workflows.py` 全量回归"。
- 影响：引擎状态改 reducer 是本批风险最高的一步（计划自己也这么写），却没有任何用例能证明"行为不变"。
- 修订：在 2.4 之前插入 **2.4a 工作流特征化测试**（纯加测试，不改代码）：条件 true / false 各一条、循环按次数与按表达式各一条、人工审核中断与 resume 一条、`input_ref` 的 `{{input}} / {{output}} / {{node_id.path}}` 各一条、`output_field` 提取一条，每条断言到 `steps` 与 `node_outputs` 的具体值。先跑绿并提交，再做 2.4。估算 1 人日。这一步同时也是 2.5 校验规则"既有图不受影响"的基线。

**D-2 1.2 依赖 1.3 才引入的配置**

- 证据：1.2 的用例"限速为 0 时按全局默认"需要 `RATE_LIMIT_API_KEY_PER_MINUTE`；1.2 的"Redis 不可用时限流放行"需要限流器本身能被整体开关；而 `RATE_LIMIT_ENABLED` 与三个上限都在 1.3 的改动清单里。
- 修订：四个限流配置项整体移到 1.2（或 1.1 的 `config.py` 改动里），1.3 只剩用户与匿名两个维度的接入。

### 3.2 P1

**D-3 1.4 缺 `max_retries` 改动点**（对应 P-1）：改动清单加 `gateway.build_llm` 设置重试次数，单元测试加"上游连接失败时 SDK 不重试"。

**D-4 2.5 的 400 契约在运行路径上不成立**

- 证据：`app/services/workflow_service.py` 的 `execute_workflow`（第 99 行起）捕获所有异常后把运行记录置 failed 并返回 200；`test_run_workflow`（第 83 行起）同样捕获后返回 `{"status": "failed"}`。计划 2.5 写"`test_run_workflow`、`execute_workflow` 经 `build_workflow` 自然校验"，但在 `build_workflow` 里抛的 `BizError(400)` 会被这两处吞掉，PRD 4.5.3 要求的"运行前校验 → 400"不会发生，还会白白创建一条 failed 运行记录。
- 修订：2.5 改动清单加"`run_workflow` 在 `create_run` 之前、`test_run_workflow` 在 try 之前显式调用 `validate_graph` 并抛 `BizError(400)`"；用例加"运行非法图返回 400 且不产生运行记录"。定时任务路径（`scheduler._run_scheduled_job`）遇到非法图仍按 failed 落库即可，计划里注明。

**D-5 FR-028 是 P0 却排在第二阶段末尾**

- PRD 第 2 节把 Prompt 模板定为 P0，计划把它放在第 12～14 步。排序理由（纯新增、可随时插队）成立，但优先级标签与执行顺序脱节会误导排期与汇报。
- 修订（推荐）：PRD 把 FR-028 降为 P1。本批 P0 的判据是"接住真实调用方"（第 1 节目标 1），Prompt 模板不满足这个判据。若坚持 P0，则计划把 2.7～2.9 提到 2.2 之前。

**D-6 1.3 缺 `Retry-After` 的实现落点**：计划写"429 由异常处理器加 `Retry-After`"，但异常处理器拿不到秒数。改动清单加 `app/core/exceptions.py`：`BizError` 增加可选 `headers` 字段，`biz_error_handler` 透传。同时 `PRD 4.1` 的 `X-RateLimit-Remaining` 在 429 时应为 0，写明。

**D-7 测试套件自身会撞用户限流，且 monkeypatch 未约束还原**

- 证据：`backend/tests/conftest.py` 的 `auth_headers` 是 session 级、单个 admin JWT；全部用例串行打同一 `user_id`。计划 1.3 写"把上限 monkeypatch 成 3"，没写用什么 fixture、如何还原。

## 6. 评审会需要当场决定的问题

1. **API Key 的归属口径**（P-2）：A 按创建人行级隔离并对 developer 开放页面；B AD 共管不隔离。推荐 A。
2. **400 / 422 分界**（P-3）：按"schema → 422、服务层 → 400"统一；CIDR 合法性与 JSON Schema 子集校验放哪一层，各定一处。
3. **`MODEL_HTTP_TIMEOUT` 是否随熔断一起下调**（P-1）：120 秒是为长回复流式输出留的；熔断只能缩短"故障后"的等待，缩短不了"第一次故障"的等待。建议保持 120 但把 `max_retries` 归零；若要更激进可把连接超时与读超时分开配置（httpx 支持），作为 FR-027 的可选项。
4. **FR-028 的优先级**（D-5）：降为 P1，或计划提前。推荐降级。
5. **`CORS_ORIGINS` 默认值**（PRD 开放问题 2）：维持 `http://localhost:18056`。同源反代部署（当前服务器方式）不受影响；`docker-compose.yml` 与 `.env.example` 给出示例即可。无异议可直接关闭该开放问题。
