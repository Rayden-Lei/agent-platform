# 文档索引

所有文档以代码现状为准，不写代码里没有的东西；尚未实现但已定稿的契约会标注"规划"。

## 阅读顺序

| 你要做的事 | 先读 |
|---|---|
| 了解平台是什么、有哪些功能、谁能用 | `01-需求说明.md` |
| 改核心链路、加模块、做技术选型 | `02-架构设计.md` |
| 建表、改列、写迁移、看 JSON 字段结构 | `03-数据库设计.md` |
| 调接口、改接口、对接前端 | `04-接口设计.md` |
| 写任何代码之前 | `05-开发规范.md` |
| 改后端 | `06-后端规范.md` |
| 改前端 | `07-前端规范.md` |
| 本地跑起来、部署、排障 | `08-运行与部署.md` |
| 看接下来该做什么、有哪些已知坑 | `09-演进路线.md` |
| 看平台离企业级中台差多远、这批补齐做什么、怎么排期 | `10-差距分析.md` → `11-差距补齐PRD.md` → `12-差距补齐开发计划.md`，评审意见见 `13-差距补齐评审报告.md` |
| 看页面为什么"像 demo"、这批深度优化改什么、进度 | `14-页面深度优化方案.md` |

## 文档清单

| 文件 | 性质 | 何时更新 |

| 01-需求说明.md | 设计文档 | 功能范围、角色权限、实现状态变化 |

| 07-前端规范.md | 规范 | 前端写法、视觉约定变化 |

| agent-platform-design.docx | 生成产物 | 01～04 改动后重新生成，不手改 |

## 生成 Word 版设计文档

```bash
backend/.venv/bin/python gen_docx.py
```

把 01～04 四份 Markdown 渲染成 `docs/agent-platform-design.docx`，随源文档改动一起提交。

## 维护约定

- 文档、代码、验证结果三者齐全才算完成一项工作。
- 改动落在哪份文档，见 `05-开发规范.md` 第 4 节的维护矩阵。
- 子目录里的 `backend/DEVELOPMENT_RULES.md` 与 `frontend/DEVELOPMENT_RULES.md` 只是铁律卡片，内容以本目录为准。
