## 3. 依赖关系与排序理由

```
1.1 入口基础（客户端 IP、共享 Redis、CORS 白名单）
 ├─ 1.2 API Key 治理字段、归属隔离与 PUT 接口（FR-026 白名单、FR-025 限流器与配置项）
 │   └─ 1.3 用户 / 匿名限流 + 状态可见 + 前端 API Key 页
 └─ 1.4 模型熔断（只依赖 1.1 的状态汇报方式，可与 1.2 并行）

2.1 摘要持久化 ──────────── 独立
2.2 工具 schema 后端 → 2.3 工具 schema 前端 + 迁移脚本
2.4a 工作流特征化测试 → 2.4 引擎 reducer 重构 → 2.5 并行节点后端 → 2.6 并行节点前端 + 编辑器拆分
2.7 Prompt 模板后端 → 2.8 智能体绑定模板 → 2.9 Prompt 模板前端 + 智能体表单

3.1 Rerank ──────────────── 前置：已配置真实向量模型
3.2 多租户设计评审 → 3.2a Alembic → 3.3 表与迁移 + 服务层过滤 → 3.4 前端；前置：触发条件（PRD 4.9.1）；排在 2.7 之后（新表也要带租户列）
```

排序理由：

- 第一阶段先做，因为它直接对应 `09-演进路线.md` 第一梯队"能被真实系统稳定调用"，且改动面最小、不碰编排引擎。
- 第二阶段内把摘要持久化（2.1）放最前：一人日、无契约变更、立刻降低长会话成本。工具 schema（2.2～2.3）其次：改动集中在两个文件。并行节点（2.4a～2.6）第三：有特征化测试与引擎重构两个前置，风险最高，放在有回归基线之后。Prompt 模板（2.7～2.9）最后：工作量最大、纯新增、不影响既有链路，可以在任何时候插队而不影响别人。
- 与 `09` 其他条目的关系：`09` 第二、三梯队里未纳入本计划的条目照旧独立推进，互不阻塞。`09` 第三梯队的 Alembic 作为 3.2a 纳入本计划，是 3.3 的前置：10 张表加列与改约束用手工脚本容易漏。

### 第一阶段：入口治理

#### 1.1 入口治理基础

目标：取客户端 IP 的唯一函数、共享 Redis 客户端、全局 IP 黑名单中间件、CORS 白名单、审计自动填 IP。本步不改 API Key 契约。

改动：

- `app/config.py`：新增 `IP_DENYLIST`、`TRUSTED_PROXY_ENABLED`、`CORS_ORIGINS`（逗号分隔，用 `field_validator` 拆成列表并校验每项是合法 CIDR / URL，非法时启动报错退出）。
- `app/core/redis_client.py`（新）：进程内单例 `get_redis()` 与 `redis_status()`（`{available, reason}`）。`services/auth_service.py` 的 `_redis / _redis_error / _mark_down / _mark_up` 迁到这里，登录限流改为调用共享客户端。行为不变。
- `app/core/request_context.py`：新增 `client_ip` contextvar 与 `get_client_ip()`；`resolve_client_ip(scope)` 按 `TRUSTED_PROXY_ENABLED` 决定取 `X-Real-IP`（无则 `X-Forwarded-For` 首项）还是 `scope["client"]`。
- `app/core/middleware.py`：`RequestContextMiddleware` 里解析并设置客户端 IP，只负责解析，不拦截。
- `app/core/ip_filter.py`（新）：独立的纯 ASGI 中间件，命中 `IP_DENYLIST` 时直接回 403 JSON `{"detail": "来源 IP 被拒绝", "trace_id"}`，`/health` 豁免。注册顺序：`add_middleware(IpFilterMiddleware)` 最先调用，使其位于 CORS 内层，403 才会带 CORS 头；请求 ID 中间件仍在最外层。
- `app/core/audit.py`：`record_audit` 的 `ip` 为空时取 `get_client_ip()`。
- `app/main.py`：`CORSMiddleware` 的 `allow_origins` 改读 `settings.CORS_ORIGINS`；按上述顺序注册 IP 过滤中间件。
- `.env.example`、`docker-compose.yml`：补三项配置示例。

测试（`tests/test_gateway_basics.py` 新）：

- `黑名单命中时登录接口403且health仍200`
- `黑名单403响应带CORS头与trace_id`

- `开启信任代理时优先取XRealIP其次XFF首项`
- `审计记录自动带来源IP`（登录成功后查 `audit_logs.ip` 非空）
- `CORS白名单外的Origin不回显`
- 既有 `tests/test_auth.py` 登录限流用例回归。

验证：pytest；curl 带 `Origin` 头看响应头；本地把自身 IP 写进 `IP_DENYLIST` 看 403。

## 5. 测试策略

- 遵守 `05-开发规范.md` 第 6 节：每条硬性规则至少一条用例，负向用例优先；断言到具体状态码、字段值、mock 调用次数，不断言"不抛异常"。
- 每步的用例名已在第 4 节列出，用例名即业务意图，落地时不得改成 `test1` 之类。
- 外部依赖：模型调用一律 mock（`ChatOpenAI` 或 `httpx.MockTransport`）；Redis 与 Postgres 用 CI 真实服务；Redis 故障场景用 monkeypatch 让 `get_redis()` 抛错。
- CI 与本地测试默认 `RATE_LIMIT_ENABLED=false`（写进 `ci.yml` 的 env 与 `tests/conftest.py`），否则整套用例串行打同一个 admin 用户会撞上用户限流；限流用例用 pytest 的 `monkeypatch` fixture 自行开启并设上限，用例结束自动还原。
- 时间相关（熔断 open 秒数、限流分钟窗口）注入可控时钟，不用 `sleep` 等待真实时间；并行节点的耗时断言用 1 秒 `sleep` 是有意为之，因为它验证的正是并发本身。
- 回归基线：2.4 提交前后 `tests/test_workflows.py` 的运行记录 `steps` 必须逐字相同。
- 迁移脚本不强制写用例：在开发库执行两次，把两次输出贴进提交说明（与第 7 节完成定义同口径）。例外是 2.3 的回填脚本，它含数据逻辑，保留用例。

| SDK 重试归零后单次网络抖动直接失败 | 偶发对话报错 | 熔断只计连续失败；`MODEL_MAX_RETRIES` 可按环境调整 |
| `CORS_ORIGINS` 默认值导致现有部署前端跨域失败 | 部署后登录页报网络错误 | 1.1 发布说明写明必须配置；`.env.example` 给出示例 |
| 熔断在真实厂商限流（429）下频繁开合 | `/system/status` 反复出现 `model_breaker` | 阈值与开启秒数可配；必要时把 429 从计数集合移除并写进决策表 |
| 多租户触发后发现服务层查询点比预估多 | 3.3 第一批资源提交超期 | 停下来重新计数并更新估算，不压缩测试 |
